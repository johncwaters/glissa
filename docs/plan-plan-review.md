# Plan: Plan Review

Status: Approved design (2026-09-07), operator answers recorded under "Decisions". The hook behaviors and the timeout ceiling were measured by the spike that opened M2 (see "Spikes").

## Why

When an agent in plan mode calls `ExitPlanMode`, the whole plan is printed into the terminal and a three-option dialog follows. Plans on this machine run 6 to 17 KB (`~/.glissa/recordings/` holds three `ExitPlanMode` requests of 6271, 8454 and 12317 chars; the trace lane recorded one of 16933). In an xterm pane that text has already scrolled and redrawn by the time the dialog appears, and on the phone layout the operator reads it through a full-bleed terminal with a key strip. Feedback goes through the dialog's single text field, one line, no reference to the section being discussed. The result is that plans get approved on a skim, or the operator walks to a desktop.

Glissa already receives the complete plan and throws it away:

- `PermissionRequest` is registered unmatched for every Claude Code session (`detection/settings-injector.ts:77`, `:124-129`), so the `ExitPlanMode` request arrives over `POST /hook/:glissaId/permissionrequest` with `tool_input.plan` (markdown) and `tool_input.planFilePath`. `HookRouter.handle` maps it to the `awaiting-input` signal and `pendingPromptKind: 'permission'` (`detection/hook-source.ts:91`, `session/adapters/claude-code.ts:65-74`) and returns `{ ok: true }` at once (`server/backend-http.ts:165-207`). Nothing reads `tool_input`.
- No `PostToolUse` matcher covers `ExitPlanMode` (`detection/settings-injector.ts:79-80`), so the approved plan is never seen either.
- The state machine has no plan concept (`shared/states.ts`, `session/core/state-machine.ts:23-70`); the card shows "Needs Input" for a permission prompt and for a plan alike.
- The dashboard has no markdown renderer and no per-session URL; the trace panel renders bodies as `<pre>` (`public/trace-panel.ts:230-240`), and hash routing exists for Settings only (`public/app.ts:489-492`, `:477`).

## Spikes

Run 2026-09-07 with `claude` 2.1.263, an HTTP hook server, and node-pty.

- Confirmed: `claude -p` has `ExitPlanMode` disabled outright ("ExitPlanMode is disabled for this session"), so the documented `defer` round trip is not a route for Glissa's interactive sessions.
- Corrected by spike 3 on `claude` 2.1.263: the approval dialog is painted the moment `ExitPlanMode` is called and stays on screen for the whole hold, footer included, and an answer of `{}` renders nothing new. Spike 1's reading that a hold hides the dialog is wrong. The hold does not gate the terminal; it only decides whether Glissa answers first, and "Answer in terminal" is a release of Glissa's hold rather than a way of surfacing anything.
- Confirmed: an approval fires `PostToolUse` for `ExitPlanMode` with `tool_response` keys `plan`, `isAgent`, `filePath`, `hasTaskTool`, and `tool_response.plan` equals the displayed plan byte for byte.
- Confirmed: text typed into the terminal during a hold is queued as a normal message ("Press up to edit queued messages"), not lost.
- Confirmed (spike 2, interactive): a bare `decision.behavior: "allow"` on `PermissionRequest` does not approve `ExitPlanMode`; the native dialog appears anyway. Approval has to carry `updatedInput`, matching the documented rule for this tool.
- Confirmed (spike 3, seven interactive runs plus a bundle read): an allow carrying `updatedInput` that echoes the received plan approves with no keystroke, and the terminal prints both "User approved Claude's plan" and "Allowed by PermissionRequest hook"; an edited `updatedInput.plan` is what the model receives, and Claude Code writes it to `planFilePath` itself and marks `planWasEdited`; a deny returns its `message` to the model verbatim as an `is_error` tool result, the model stays in plan mode and resubmits within seconds, and no `PostToolUse` fires for the denied call; `updatedPermissions` `setMode: acceptEdits` switches the session, with `PostToolUse` reporting `permission_mode` `acceptEdits`.
- Confirmed: the http hook `timeout` has no clamp anywhere in the 2.1.263 bundle, and 86400 was honored live. When the timeout does fire, Claude Code silently destroys the socket, renders nothing, leaves the dialog exactly as painted, and produces neither an error nor an implicit deny; a reply written afterwards reaches a destroyed socket and is discarded. So a held reply must be written at most once and never after the socket closed.
- Confirmed (spike 4, experiments O and P): a terminal answer during a hold completes the tool call and fires `PostToolUse` within 40 milliseconds, and Claude Code neither cancels nor closes the outstanding hook request, which was still open a minute later. So `PostToolUse` on an `open` review is the only signal that the decision was made elsewhere, and the lane releases the held reply itself on it. A hook decision arriving after the terminal already answered is accepted by the socket and discarded, with no second approval and no error, so a late write is harmless; a terminal approval is told apart by rendering "User approved Claude's plan" with no "Allowed by PermissionRequest hook" line.

## What already exists

Reuse, do not rebuild:

The `ExitPlanMode` request needs its own `PermissionRequest` entry pointing at a second URL, `<hook base>/permissionrequest-plan`, with a long timeout, plus its own `PostToolUse` matcher. The plan endpoint is a second URL, not a second handler on the same URL: a matcher-scoped entry does not shadow the unmatched one, Claude Code runs every matching hook in parallel, and a `PermissionRequest` payload carries no tool-use id, so two entries on one URL would arrive as two indistinguishable posts and the lane could store two revisions and hold two replies. The unmatched `PermissionRequest` entry is left exactly as it is and keeps answering at once for every tool, `ExitPlanMode` included, so the status signal path is unchanged and only the plan endpoint holds and stores.

## Design

### The decision flow

1. Claude calls `ExitPlanMode`. The `PermissionRequest` hook posts the payload. The existing route in `server/backend-http.ts` only forwards the event, the glissaId, the payload and a reply promise slot to an injected plan-review dependency, `planReview.onHookEvent`, exactly as it already forwards pack notices; the `ExitPlanModeInput` parse, the revision store and the held-reply registry live in `server/plan-review-wiring.ts` on `server/core/plan-review-core.ts`. The lane parses `tool_input` through a Zod schema `ExitPlanModeInput` (`plan: string`, `planFilePath: string`, plus the optional `agent_id` and `agent_type` common input fields read from the payload) and fails closed: an unparseable body is handled exactly as today (reply at once, terminal dialog appears).
2. The plan-review lane appends a revision `{ sessionId, revision, plan, planFilePath, receivedAt, agentId: string | null, agentType: string | null }`, both agent fields written at receive time from the hook payload because the store is append-only and nothing can be filled in later, to `~/.glissa/plans/<sessionId>.jsonl` and keeps the open review in memory. The session is already `WAITING`; `pendingPromptKind` becomes `'plan'` (adapter: `mapHookPromptKind` returns `'plan'` when `tool_name === 'ExitPlanMode'`). A `session-plan-changed` push carries `{ id, agentId, revision, state, chars, title }` only, never the body.
3. The HTTP reply is held until a decision arrives. There is no cap and no connected-client gate: the operator chose that every plan approval goes through the dashboard, so a plan waits for a dashboard decision, for the "Answer in terminal" action, for the session to exit, or for the server to shut down (the pending replies are flushed with `{}` before the listener closes; a crash means Claude sees a connection failure, which is documented as non-blocking and falls through to the dialog). The hook entry's `timeout` is 86400 seconds, verified honored with no clamp, and Glissa keeps one release of its own against it: 60 seconds before that `timeout` would fire, the lane writes the verified `{}` itself, so the release always runs through the tested path and never through a silent socket abandonment. That release is the hook's ceiling, not an operator-facing cap. A terminal-only operator is never blocked, because the approval dialog is on screen from the moment `ExitPlanMode` is called; the hold only decides whether Glissa answers first. The `WAITING` notification names the plan the moment it arrives, and "Answer in terminal" releases Glissa's hold at any time. Fail open in every path. Each review carries its own `state` of `open`, `released`, `decided` or `closed`, pushed to every surface through that review's `session-plan-changed` summary, and each action bar renders from its own review's `state` alone. Releasing the hold for any reason moves that review to `released`, so its action bar turns read-only and shows "Answer in the terminal" as status text while any other review of the same session stays actionable.
4. The operator opens the plan on desktop or phone, reads it whole, and sends one `plan-decision` client message `{ id, agentId, revision, decision, feedback?, plan? }`:
   - `approve`: reply `decision.behavior: "allow"` with `updatedInput: { plan, planFilePath }` echoing the plan (a bare allow leaves the dialog up, spike 2; the echo is also the edit channel).
   - `approve-accept-edits`: the same plus `updatedPermissions: [{ type: "setMode", mode: "acceptEdits", destination: "session" }]`, the hook form of "Yes, auto-accept edits" (unverified, M2 spike).
   - `revise`: reply `decision.behavior: "deny"` with `message` set to the composed feedback. Claude stays in plan mode, revises, and calls `ExitPlanMode` again, which arrives as revision n+1 and reopens the review with a diff against revision n.
   - `terminal`: reply `{}`.
   The moment the held HTTP reply is written, or its connection aborts, the review leaves `open`: it moves to `decided` after an allow or a deny and to `released` after a pass-through or an abort, and no later decision is accepted. A decision naming a revision other than the open one is refused with `session-error`, so a phone that lagged behind a resubmission cannot approve the wrong text. A decision on a released revision, or on any revision whose review is no longer open, is refused the same way.
5. `PostToolUse` for `ExitPlanMode` arriving on a `decided` review records the approved text from `tool_response.plan`, whichever surface approved it, and moves that review to `closed`, freeing its in-memory entry. The next `PermissionRequest` on a `decided` review, the normal sequel to a deny, opens the next revision on that same review. Neither is guaranteed to follow a decision: Claude Code re-evaluates configured ask and deny rules after an allow, and the operator can interrupt the pending tool call, so a review left in `decided` with neither arriving is closed on a turn-end hook, a subagent's review on the `SubagentStop` whose `agent_id` matches it and the main agent's review on `Stop`, both already registered (`detection/settings-injector.ts:77`). A terminal "Tell Claude what to change" produces no `PostToolUse`; the next `PermissionRequest` is simply the next revision. A released review closes on the same signals, whichever of `PostToolUse` or the next revision arrives first. `SessionEnd` and process exit close an open review as abandoned.

Hooks fired inside a subagent carry `agent_id` and `agent_type` among the common input fields, so `ExitPlanModeInput` reads both from the payload and the revision record stores `agentId` and `agentType` at receive time. The held-reply registry is keyed by glissaId plus agentId, null for the main agent, so concurrent subagent plans hold, release and close independently, and the view labels a revision carrying an agentId as that agent's plan. A headless child cannot reach this path at all, because `claude -p` has `ExitPlanMode` disabled (spike 1). An in-process subagent that did call it is held like the parent's plan and released by the same actions.

### Feedback in tandem

The reply on `revise` is the "No, keep planning" channel, so feedback quality is the whole product here, and section comments landed first in M3. The view renders the plan by section (`splitPlanSections`: every heading opens one, and what stands before the first heading is the preamble) and gives each section head a constant-label "Comment" affordance, which opens the same modal the phone uses as a sheet; a comment on the preamble is a comment on the whole plan, carried as `heading: null`. The pending count rides the status text beside the action bar, never a button label. "Send feedback" collects the general text through that modal and sends `revise` with both `comments` and `feedback`. The pure `server/core/plan-feedback-core.ts` composes the deny message: the header `Feedback on plan revision N:`, then one block per commented section quoting its heading, then the general text, then `Revise the plan and present it again.`; a revise with nothing typed says `No detail was given.` rather than denying with an empty message. That composed message is capped at `PLAN_HOOK_OUTPUT_MAX_CHARS`, 10000 characters, because Claude Code replaces a longer hook output with a preview and a file path ([hook JSON output](https://code.claude.com/docs/en/hooks#json-output)) and three full-length comments already pass it; a `revise` composing more is refused with a plan-scoped `session-error` instead of being sent half-read, and the face refuses the same budget before it sends. The agent gets structured, addressed feedback instead of one line, and the next revision can be diffed against the one the comments referred to.

Editing the plan directly is the second channel, the hook form of the terminal's Ctrl+G. "Edit plan" swaps the reading column for a textarea over the markdown of the selected open revision (phone keyboards handle it), and a constant-label "Read plan" control returns to reading without sending. Approving from the editor sends the edited text as `plan`, which the server places in `updatedInput.plan`; an editor left untouched sends no `plan` at all, so an unedited approve still echoes the received bytes. The server takes an edit only on the open revision of an open review, refusing one over `PLAN_BODY_CAP_BYTES` by UTF-8 length rather than writing it into the reply. Glissa never writes the plan file: Claude Code writes `updatedInput.plan` to `planFilePath` itself and marks `planWasEdited` in `PostToolUse` (spike 3, H), so the file rewrite and its containment check are dropped. Glissa also never re-reads that file to build the echo, because whatever the file holds at that instant would become the approved plan, which would launder a third-party edit into an approval; the bytes it echoes are the bytes the request carried. A decision carrying an edited plan is also the largest frame the control WS takes, so that socket's `maxPayload` is `CONTROL_FRAME_MAX_BYTES` in `shared/contracts/control-messages.ts`, derived from the plan caps rather than written by hand: the body cap plus the feedback and comment caps, doubled for JSON escaping, plus a fixed envelope. The 16 KB default it replaces closed the socket on any edited plan over about 16 KB, losing the decision while the send reported success and leaving the hook held; the face refuses a decision over that same budget, so nothing reaches a frame the socket will not take.

Between a `revise` and the next submission the agent rewrites the plan file (observed in the trace: two `Write` calls to the same `~/.claude/plans/<slug>.md` in one planning turn), so a watch on that one file is the only signal that the next revision is being written, and the chip that signal raises is the whole point of the watch. That watch is registered on the file's PARENT DIRECTORY and filtered by basename, because `fs.watch` on a path follows the original inode: the agent's rewrite is a delete and recreate, so a watch on the file itself goes deaf after the first replacement while a same-path revision keeps it ([Node inode behavior](https://nodejs.org/api/fs.html#inodes)). The `session-plan-draft` notice is body-free and stays out of `REFRESHABLE_TYPES`, so backpressure never drops it, but it is not replayed either: a control socket that disconnected or was closed at the hard backpressure ceiling misses it outright, and the reconnect pull repairs the review index and the selected body only, so that session's chip comes back on the next write to the plan file rather than from the pull. The watch outlives a `revise` decision, which is exactly when the next draft is written, and dies with the review. A draft body is read only from the path the hook delivered, never a path a client names, and only through the containment routine both lanes share (`openContainedFile` in `server/contained-file.ts`) rooted at `<Claude config home>/plans`, or the chip becomes a file-read oracle over an account holding `.credentials.json`, `settings.json` and every transcript; the cost of that one root is that a plan file a project keeps outside it is refused, and since the same containment runs at WATCH START, such a session raises no chip at all rather than a chip that yields nothing. A file that is not there yet keeps its watch, since its directory is contained and the next write is what a rewrite looks like, while every other refusal disables that review chip alone, never the lane, exactly as a watch error does. A draft carries `revision: 0` because it is bytes the agent never submitted, so it renders read-only and decides nothing. Before the first submission there is no supported signal and none is invented. Pinned by `tests/backend-plan-draft.test.ts` and `tests/frontend-plan-face.test.ts`.

The revision diff is the third channel. The pure `public/plan/plan-diff-core.ts` trims the common prefix and suffix in one linear pass, then runs a longest-common-subsequence pass over what is left, so an identical or append-only pair costs one walk and a shared prefix keeps a long plan diffable. The changed middle is capped at `PLAN_DIFF_MAX_LINES` lines across both sides, which bounds the comparison at a million cells; over the cap the view says the diff is too large and shows the newer body whole. A constant-label "Diff" toggle in the plan head renders the selected revision against the previous one, pulling that previous body once through the ordinary `session-plan` request without moving the selection a decision would name. `public/sidebar/diff-core.ts` parses unified diffs and computes none, so nothing there is reusable.

### Surfaces

Desktop: the plan lives inside the Focus center, not in a new tab. The session card owns the swap: `public/session-card/` gains a plan face beside its terminal face, toggled by card-level state, so whichever surface has borrowed the card, the Focus center card area or the phone Terminal screen, shows the same face. The Focus center and the phone screen only ask the card to show its plan face and never reach inside the borrowed card. The plan face shows only while the card is borrowed, because that face choice is card state scoped to the borrowed condition: `releaseCard` returns the card to the desktop sessions grid (`public/card-host.ts`, `public/session-card/card-registry.ts:63`), and that release restores the terminal face, so the reading column and the decision bar never land inside a grid tile. A card in the grid always keeps its terminal face and shows the "Plan ready" badge when `pendingPromptKind` is `'plan'`; focusing it is what brings the plan face up. While a borrowed card has an open review it shows its plan face in place of the terminal, with a constant-label "Terminal" control that swaps back and a "Plan" control that swaps in again. The card overflow menu gains a "Plan" item for any session whose snapshot carries `hasPlan: true`, so an approved plan stays readable after the review closes. That flag rides the session snapshot and the `session-plan-changed` summary because nothing else on the wire carries it, and the lane fills it from one `readdir` of `~/.glissa/plans` at lane start held as a session-id set it updates on append and on prune, never from a per-session filesystem check on a render path. Layout inside the plan face: a reading column of at most 72ch, a heading rail on the left that scrolls the column, revision picker and a diff toggle in the section head, a sticky action bar at the bottom with the decisions. A session lists one review per agent, the main agent's and one per subagent that called `ExitPlanMode`, labeled by `agentType`, each with its own revision picker and its own action bar, and a decision acts only on the review it sits under. Rendering goes through a pure `public/plan/plan-markdown-core.ts` producing a block tree (ATX headings, paragraphs, ordered and unordered lists with indent nesting, fenced code, tables, blockquotes, rules, inline code, emphasis, links), turned into DOM with `el()` and `textContent` only; no HTML from the plan is ever parsed. `plan-markdown-core` accepts only `http:` and `https:` for an `href` and renders every other link as plain text, so it never emits a `javascript:` or a `data:` URL into the dashboard origin, and external links open with `rel="noopener noreferrer"`. `tests/frontend-plan-markdown.test.ts` pins this with a `javascript:` case and a `data:` case. No dependency is added.

Phone: no new screen. The phone Terminal screen already borrows the whole card, so it shows the card's plan face and adds nothing of its own. A Board row (attention state "Plan ready" joins the existing "needs you" ordering, with no new rule), the Terminal screen top bar action and a notification tap through the deep link `#plan/<sessionId>` all open the Terminal screen with the plan face showing. The action bar is thumb-reachable at the bottom; section comments open in a sheet; the editor is the same textarea full-bleed. The key strip is not involved.

Buttons carry constant labels: "Approve", "Approve and accept edits", "Send feedback", "Answer in terminal", "Edit plan". Progress and revision counts live in status text beside them.

Notification: the existing `WAITING` notification gains plan copy ("Plan ready for review: <title>") when the kind is `'plan'`, and its click target is the deep link.

The plan file path is derived through `isSafePathSegment` (`server/core/upload-core.ts:64`) before the session id is joined into `~/.glissa/plans/`, exactly as the trace lane derives its own (`server/trace-wiring.ts:247-250`), and `session-plan-response` reads one revision by a byte offset recorded at append time, never by parsing the whole file, matching `readSessionTracePage` (`server/core/session-trace-core.ts:127`). The approved plan stays readable after the session ends through the card overflow "Plan" item; a removed session's file stays on disk under retention with no surface.
- Config: `planReview: { enabled: true }` in `shared/contracts/config.ts`, a settings row in the machine level. Off means the plan endpoint answers `{}` at once and the view stays read-only.
- Hook settings: a `PermissionRequest` entry `{ matcher: 'ExitPlanMode', url: <hook base>/permissionrequest-plan, timeout: 86400 }` beside the unmatched entry, which is left exactly as it is; the event segment of the existing `POST /hook/:glissaId/:event` route is free-form today, so `permissionrequest-plan` needs no new route and the route itself gains one injected dependency and no new URL handling. `ExitPlanMode` gets its own `PostToolUse` entry beside the wakeup matcher, pointing at a second free-form segment, `<hook base>/posttooluse-plan`. The hook route's body cap rises from 64 KB to 512 KB on the plan segments alone, because a dropped body today destroys the request silently, while the shared `PostToolUse` segment carries every session's tool results and keeps the 64 KB cap.

## Decisions

Operator answers of 2026-09-07 that settled the review rounds' open questions:

- Hold always, with no cap. Every plan approval goes through the dashboard; the hold ends on a dashboard decision, on "Answer in terminal", on a session exit, on a server shutdown, or on the lane's own empty reply written 60 seconds before the hook timeout would fire, with the hook timeout itself as the final fallback behind it. The connected-client gate and reconnect grace proposed during review are dropped.
- Keep all three tandem features: the revision diff, the plan-file watch with its draft chip, and "Approve and accept edits".
- Section comments land first in M3, then the editor.
- The plan lives inside the Focus center on desktop, not in a new primary tab.
- Approved plans stay readable after the session ends, from the card overflow menu, backed by the per-session file on disk.
- `AskUserQuestion` stays a separate plan.
- The three slices below are build order only; the whole design ships.

## Risks

- Claude Code changes `tool_input` field names: the schema fails closed and the request behaves as today.
- A hold outlives the hook `timeout`: the entry carries the measured 86400 second value, and the lane writes its own verified `{}` 60 seconds before that timeout would fire, so the release always runs through the tested path.
- Hook timeout semantics change: the lane's own `{}` written 60 seconds early narrows the race but does not remove it, because a stalled event loop or a sleeping host can let Claude Code's own timeout win first. A fired timeout is a silent abandonment of the request rather than a deny, so the fallback behind the lane's release is the dialog that is already on screen.
- An operator approves in the terminal while the phone shows the review: `PostToolUse` closes the review on both.
- A plan over the body cap: the cap is raised for this route and a rejected body is logged with its size instead of destroyed silently.
- Nobody opens a client: nothing is lost, because the approval dialog is live in the terminal throughout the hold. The hold only delays whether Glissa answers first, and the operator can answer where they are; the notification and the constant-label "Answer in terminal" action are the routes back to the dashboard's copy of the decision.
