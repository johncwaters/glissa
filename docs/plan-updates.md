# Plan: Dashboard Updates

Status: shipped 2026-09-05, all three milestones (commits 528957a U1, 8594be6 U2 and U3). Held for the operator: the necessity cuts listed in the U1 and U2 commit reports.

## Why

Updating a running Glissa is the one operator task the dashboard cannot do. The update check (`server/backend-update.ts`, `server/update-check.ts`) produces a banner whose only affordances are Copy, Dismiss and a release link (`public/index.html:169-175`, `public/app.ts:381-414`). Everything after the copy is manual: open a terminal in the main checkout, confirm a clean tree, `git pull --ff-only`, `npm ci`, `npm run build`, then `systemctl --user restart glissa`. In practice that sequence is delegated to an external agent every time, and the agent cannot even finish it, because a restart kills the cgroup it lives in (`KillMode=control-group` in the operator's `glissa.service`), so the last step is handed back anyway.

Three concrete costs:

- Discoverability. The banner names a version and a shell command. Nothing in Settings shows the installed sha, the branch, the last check time, or whether the tree is clean. An operator cannot tell "up to date" from "check disabled" from "check failed".
- Ceremony. Four commands and a restart, run by hand or by an agent, for a change that is otherwise one click.
- Failure handling. A failed `npm ci` or build leaves the checkout half updated with no record. `dist/` is wiped at the start of every build (`scripts/build.mjs:53`) while the server serves relays, pack specs and the dashboard from it, so a rebuild beside a running server is a self-inflicted outage window until restart.

## What already exists

Reuse, do not rebuild:

- Check and status: install flavor, installed sha, latest release tag from `git ls-remote` with a GitHub API fallback, a 6h throttle in `~/.glissa/update-check.json` that `checkForUpdate` bypasses when handed `ttlMs: 0` (`server/update-check.ts:185`), a daily recheck while a dashboard is connected (`server/backend-update.ts:59-68`). Status replays to every new control client (`server/control-handlers.ts:1003-1006`), wire shape at `shared/contracts/control-messages.ts:305`.
- Restart: the `restart-server` control message (`server/control-handlers.ts:909,984`, confirm dialog with the session count at `public/app.ts:681-696`) tears everything down and then exits 75 under systemd so `Restart=on-failure` brings the unit back, or respawns detached elsewhere (`server/server-lifecycle.ts:117-153`, `server/core/restart-strategy.ts`). Pinned by `tests/server-lifecycle.test.ts`.
- Recovery after restart: auto-resume respawns every project that had both `wasActive` and a persisted `resumeSessionId` (`session/core/auto-resume.ts:14-27`); the dashboard reconnects with backoff and hard-reloads whenever `serverBuild` changes, which it does on every boot (`server/backend.ts:65`, `public/server-build-core.ts`). No old client can outlive a restart, so no wire-compat window is ever needed.
- Git parsing: `server/core/branch-sync-core.ts` already exports `parseLeftRightCount`, `parseRemoteFromUpstream`, `buildResyncCommand` for `merge --ff-only`, and `firstGitErrorLine`, all pinned by `tests/branch-sync-core.test.ts`. Porcelain dirtiness is an emptiness check (`server/git-workspace.ts:227`), and worktree add and prune already run there under one serial queue.
- Persistence and single-flight: `createJsonStateWriter` (`server/json-file.ts:148`) is an atomic, chained, mkdir-ing JSON writer; `server/rtk-install-wiring.ts:46` is a working single-flight IO lane whose status object renders beside a settings row (`public/settings-panel.ts:433`).
- Dashboard: the declarative settings map with read-only rows and a live per-setting status slot (`public/settings-map.ts`, `public/settings-panel.ts`); the pure update helpers and their tests live in `public/radar-core.ts:426` and `tests/radar-core.test.ts`; the clipboard helper at `public/dom-helpers.ts:92`.
- Child processes: `server/child-process-safe.ts` is the only importer of `node:child_process`; async `execFileAsync` for anything on the event loop.

So the missing piece is one thing: an apply step between "update available" and "restart", and a place in Settings to see and drive it.

## Decisions

1. Clone flavor on Linux and macOS gets the apply button. The operator's servers are clones under systemd (`docs/distribution.md`). npm-global installs keep today's copy-the-command banner, and so does a Windows clone: `npm` there is a `.cmd` launcher with no safe `execFileAsync` form, and renaming `node_modules` under a process holding node-pty's loaded native module fails.
2. Stage in an isolated worktree, hand off by fast-forward plus renames. The lane asks `server/git-workspace.ts` for a detached worktree of the target sha at `.glissa/update/next/` inside the package root, sharing a filesystem with `dist/` so no rename crosses one. It installs and builds in there, so the live checkout, its `node_modules` and its `dist/` stay untouched until the handoff merges and renames the staged output into place. `scripts/build.mjs` needs no change: it derives its output from its own location (`scripts/build.mjs:7`), so a build in the staging worktree, the implicit `prepare` build during `npm ci` included, lands in `.glissa/update/next/dist/`. `.gitignore` gains `.glissa/update/`, without which the clean-tree preflight refuses every update after the first (`server/git-workspace.ts:225` passes `--untracked-files=all`); staging under the `.glissa` segment also inherits the ignore lists that hardcode it (`server/core/ingest-fs-core.ts:46`, `server/post-turn-checker.ts:75`), so fs ingest never watches the staged copy and the post-turn checker never rewrites it.
3. Nothing live changes before the handoff, so there is no revert path. A failed fetch, `npm ci` or build deletes `.glissa/update/next/` and journals it; HEAD, `node_modules` and `dist/` were never touched, so what boots next is what was already running. The operator's unit rebuilds on every start (`ExecStartPre=npm run build`, verified on this host, absent from `docs/distribution.md:12` which is stale on that point), and a failed stage cannot crash-loop that build, because HEAD never moved.
4. Preflight refuses rather than repairs. Clean tree, a checked-out branch with an upstream, fast-forward possible. Each refusal is a named reason with the fix in plain words; the lane never stashes, resets a dirty tree, or force-pulls.
5. Fast-forward only, to a fixed target. The target sha is captured at check time and shown in the UI. The lane fetches and stages that sha, and the handoff merges `--ff-only` to it, so what runs is what the operator saw. A status carrying no sha (the GitHub API fallback returns none) disables Update with the reason `target sha unknown, check again`.
6. `npm ci` only when the lockfile changed between the old and new sha. Native node-pty compiles are the slow, fragile part; skipping them when nothing changed makes the common update take seconds.
7. Channel is a flat config key beside `checkForUpdates`: `updateChannel` is `release` (default, today's tag semantics) or `main` (the upstream of the checked-out branch, refused with a named reason when that branch has no upstream). The main checkout currently sits 7 commits past `v0.24.2` with no banner, which is correct under `release` and invisible under nothing else. The status records the channel it came from; saving a different `updateChannel` clears it and triggers a check, and the apply preflight refuses with a named reason when the status channel is not the configured one.
8. One update at a time, journaled at `~/.glissa/update-journal.json`: from sha, to sha, to version, channel, step, per-step status, tail of output, started and finished times. Terminal states are `staged` (built, ready for a handoff), `succeeded` (handed off), `failed`, `interrupted` and `discarded`. The persisted journal is progress replay for late clients and nothing more: the lane holds the run in an in-memory staged descriptor (from sha, target sha, lockfile changed, staging path, state), and the handoff reads that descriptor, validated against the staging worktree's HEAD, never the file. Its shape is a Zod schema in `shared/contracts/`, as the repo requires of every persisted shape, read back with `safeParse` so a malformed or older file fails closed to a display-only `interrupted` record. Its writer takes a `warn` that marks the run failed, so a persistence failure fails closed rather than being swallowed (`server/json-file.ts:148` defaults `warn` to a no-op).
9. Same trust as restart. A paired remote client can already restart and spawn sessions; the code an update pulls comes from origin, not from the client, so `update-apply` is not hidden from remote.

## Milestones

### U1: Apply lane (server)

1. `server/core/update-apply-core.ts` (pure): `decidePreflight(facts)` returning the step list or a named refusal; `planSteps({ lockfileChanged })`; `planHandOffRenames({ lockfileChanged })` returning the rename sequence and the reversal for a failure at each one; journal transitions. Parsers come from `branch-sync-core.ts`, not new code.
2. `server/update-apply.ts` (IO): a step sequencer over `execFileAsync` shaped like `rtk-install-wiring.ts` (one `inFlight` flag, a status object). Every git step goes through a serialized member of `server/git-workspace.ts`, which runs it on the engine queue and so serializes against the integration sync lane's `merge --ff-only` in this same checkout (`server/git-workspace.ts:524`); a private flag would not. `npm ci` and the build run outside that queue under `inFlight` alone, so a 15 minute install never blocks session worktree creation, branch sync or the PR poller. Steps: preflight through `probeWorktreeDirty`, fetch through `fetchOrigin`, stage the worktree, then build in it. Lockfile differs between HEAD and target: `npm ci` there, whose `prepare` script builds (`scripts/prepare-build.js` runs `npm run build` unconditionally). Lockfile unchanged: a `node_modules` symlink to the live one and an explicit `npm run build`. Any failure removes the staging worktree through `removeWorktreeByPath` and journals it. A second `update-apply` is refused with a named reason while the descriptor reads `staged` (restart to hand it off) and once a restart has been requested, so no run meets `git worktree add` on a non-empty path and no handoff meets a staging worktree whose `npm ci` is still writing. Constructed in `server/backend.ts` beside `createBackendUpdateCheck` (line 251), where `httpServer`, the assembled `gitWorkspace` (line 190) and `createLifecycle` (line 293) are all in hand, reaching the handlers through `server/backend-control.ts` (`applyUpdate`, `getUpdateJournal`, `handOffStagedUpdate`, injected the way `getUpdateStatus` is). Journal via `createJsonStateWriter`; `update-progress` after every transition. Per-step timeouts (fetch 60s, merge 30s, `npm ci` 15min, build 10min); output kept to the last 200 lines.
3. `server/git-workspace.ts` gains three serialized members on the object `createGitWorkspace` returns, the only way in, since its `engineQueue` (line 262) is a closure local and that factory is the only export: `stageDetachedWorktree({ projectPath, path, sha })`, so this stays the only module running `git worktree`; `mergeFastForwardTo({ projectPath, expectedHead, sha })`, which refuses unless the HEAD it reads under the lock equals `expectedHead` and then runs `merge --ff-only`; and `resetKeepTo({ projectPath, sha })`. The rest the lane needs is already a serialized member: `removeWorktreeByPath` (line 832) for cleanup, `fetchOrigin` (line 855) for both the lane and the update-check path, `probeWorktreeDirty` (line 822) for preflight and the handoff re-check. Nothing hands the queue out, because every public member is wrapped by `serialized(...)` on one non-reentrant queue (lines 264 and 1039-1052) and nesting one inside another would deadlock. Renames need no git lock and run in the lane after the merge member returns. No build config changes anywhere.
4. Handoff: `LifecycleOptions` (`server/server-lifecycle.ts`) gains an optional `beforeHandOff` callback, bound by `server/backend.ts` to `handOffStagedUpdate`; both call sites keep working with it absent (`server/backend.ts:293`, `server/main.ts:105`). It runs exactly once, awaited after `awaitTeardown` from whichever of the `httpServer.close` callback and the fallback timer fires first: control sockets stay connected through teardown and nothing in `createBackendShutdown` terminates them, so `close` may never call back and the fallback timer would otherwise skip the callback outright (`server/server-lifecycle.ts:155`). It swaps only when the in-memory descriptor reads `staged` and the lane is idle, and otherwise removes the staging worktree and hands off unswapped. Its timeout bounds only the wait for `mergeFastForwardTo` to reach the front of the engine queue, because no promise timeout cancels a merge or a rename; once that member runs, the merge-and-rename sequence runs to its settled result, reversal included, before the lifecycle exits. The sequence: `probeWorktreeDirty` re-checks the live tree, `mergeFastForwardTo` merges to the descriptor's target sha with its from sha as `expectedHead` and reports the HEAD it sampled under the lock, then two renames per artifact, `dist` out to `.glissa/update/prev-dist` and the staged `dist` in, plus `node_modules` out to `.glissa/update/prev-node_modules` and the staged one in when the lockfile differed. Any failure reverses the renames already done and, only when that merge moved HEAD, runs `resetKeepTo` to the sampled HEAD, so a commit the integration sync lane landed meanwhile is never dropped. Every reversal result is checked; one that fails writes a marker under `.glissa/update/` naming what to restore. The reason is journaled and the handoff proceeds either way, so no dashboard is stranded behind the `restarting` frame (`server/control-handlers.ts:909`). Both rename windows and any marker are repaired by `scripts/recover-handoff.mjs`, dependency-free (plain `node:fs`, nothing imported from the package), which restores `prev-node_modules` or `prev-dist` when the live one is missing and runs from `package.json`'s `start` script before `dist/server/index.js`. Boot runs exactly one git operation, `removeWorktreeByPath` on a stale staging worktree, and no npm: once the HTTP server is listening, the way `server/session-registry.ts:196` defers auto-resume onto that event, the lane marks a journal left mid-run failed with the reason `interrupted`, marks a `staged` journal `discarded` with the reason `restarted without handoff` for the Settings row, then removes the worktree and clears `.glissa/update/`.
5. Control messages (`shared/contracts/control-messages.ts`, `server/control-handlers.ts`): requests `update-check` (a new `checkNow(ttlMs: 0)` on `BackendUpdateCheck` in `server/backend-update.ts`, injected beside `getUpdateStatus`) and `update-apply`, with `restart-server` refused by a named reason while the lane is staging; broadcasts `update-progress` (journal projection) and `update-status`, which replaces `update-available` outright and adds installed branch, upstream, tree cleanliness, last check time, channel and journal summary. `backend-update.ts` splits recording from surfacing: every result is recorded with its check time, up to date and failed checks included, and `update-status` goes out on each, while the banner log and the dedupe stay behind `updateAvailable`. Today `surfaceUpdate` (`server/backend-update.ts:36`) returns before recording, so `checkNow` would leave the stale status the snapshot replays (`control-handlers.ts:1003`). Both consumers move with the broadcast: the banner and the Radar ops row (`applyRadarUpdate`, `public/app.ts:318`). The snapshot replays progress and status alike.
6. `server/update-check.ts`: one branch for clone flavor on channel `main`, where latest is the upstream of the checked-out branch: `git ls-remote <remote> refs/heads/<branch>` plus `parseLeftRightCount` over `git rev-list --left-right --count HEAD...<sha>` after a fetch. It only gathers facts; the verdict stays pure in `decideUpdateStatus` (`server/core/update-core.ts:140`), extended with channel and behind count. The 6h cache record carries its channel and is ignored when that does not match the configured one.
7. Config: `updateChannel` in `shared/contracts/config.ts`, its default in `DEFAULT_CONFIG` (`server/config-store.ts:23`) and in the `getSettings` projection (`server/config-store.ts:400`), hot-applied on settings save the way the other flat keys are, with round-trip coverage in `tests/config-store.test.ts` and `tests/control-settings.test.ts`. The settings row is milestone U2's.
8. Tests: `tests/update-apply-core.test.ts` (preflight refusals, step planning with and without a lockfile change, the rename plan and its reversal, journal transitions); `tests/update-apply.test.ts` over a fake `runCommand` and fake fs (staging writes nothing under the package root outside `.glissa/update/`, both lockfile paths, rename order, reversal at a failure on each rename, `resetKeepTo` only when the handoff merge moved HEAD, boot marking an interrupted journal failed, single-flight); channel and behind-count verdicts in `tests/update-core.test.ts`; `beforeHandOff` awaited and timed out in `tests/server-lifecycle.test.ts`; the three new members in `tests/git-workspace-session.test.ts`; `tests/control-update-available.test.ts` moves to `update-status`; the contract tests pick up the new shapes.

Done when: from a clean clone behind origin, sending `update-apply` over the control WS produces a green journal and a built `.glissa/update/next/dist/`, `restart-server` hands that build over and comes back on the new sha, a failed stage leaves HEAD, `node_modules` and `dist/` exactly as they were, and every refusal path yields a named reason without touching the tree.

## Out of scope

- npm-global self-update from inside the running process.
- Windows service management; the respawn strategy already covers a detached process. A Windows handoff is out too: U1 covers clone installs on Linux and macOS, and a Windows clone keeps the copy-the-command banner until one exists.
- Preserving live terminals across restart. Resume is by conversation id and stays lossy.
- Automatic updates without a click. `checkForUpdates` remains a check, not an apply.
- A separate rollback control and a post-restart verdict: decision 3 makes both unnecessary.

## Risks

- Each artifact carries a residual window between renaming the live one away and renaming the staged one in, and `node_modules` is the worse of the two: no dependencies means the unit's rebuild-on-start cannot find vite and the unit loops. Both are closed by `scripts/recover-handoff.mjs` on the next start; a unit whose `ExecStart` bypasses `npm start` has to call the shim itself, a dotfiles change this repo cannot make.
- `npm ci` on a node-pty bump can take minutes and needs build tools; the step timeout and the output tail are what make that failure legible instead of silent.
- Rename across filesystems is not atomic; `.glissa/update/` is created inside the package root beside `dist/`, so it never crosses one.
- A remote client applying an update while a local operator is mid-session: single-flight plus a broadcast journal means both see the same thing; the restart confirm names the sessions either way.
