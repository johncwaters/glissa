design review

Glissa Architecture Review

Each subsystem of Glissa compared against the established pattern for its problem class: event handling, pollers, webhook-grade signal ingestion, completion detection, notification delivery, state machines, local persistence, branch integration, and localhost security. The left diagram is what is built; the right is the reference shape from current practice. Verdicts are honest both ways: several Glissa designs already match the canon, and several "correct" patterns would be overkill for a single-process, single-operator tool. Sources are linked per section.

VerdictMeaning
matchesAlready the best-practice shape, or a deliberate documented tradeoff that current practice endorses for this context.
considerA named pattern would improve robustness or simplicity; not broken today.
gapA real hole with a concrete failure mode the reference pattern closes.

1. Transport and fan-out

Two WebSockets plus HTTP ingresses, with backpressure on the byte stream and a replay log on the control stream.

as built
reference
  • matchesBackpressure and replay retention are canonical, on the DATA stream. bufferedAmount gating (ws-sender drops recoverably from the ring and closes stalled sockets), and a control replay log that retains only the one-shot message types a connect snapshot cannot reconstruct, are exactly the published guidance.
  • keepTwo sockets are load-bearing, not accidental. Reviewed against a single merged socket and the split stays, for four reasons. The channels want opposite loss policies: data bytes drop recoverably from the ring and backfill by offset, control JSON must not drop and replays one-shot types, and bufferedAmount is per-socket, so one shared buffer could not tell which class is stalled. One WebSocket is one TCP stream with no prioritization, so a session flooding PTY output would head-of-line-block a kill ack or notify frame behind scrollback. The data path is a raw byte pipe with zero framing; merging adds a demux protocol (session-id framing or JSON plus base64 at roughly 33 percent overhead) and subscribe messages. And the lifecycles differ: data is per session per viewer (viewer-size arbitration keys on that connection), control is one per client. The cost of the split is N+1 sockets per client, a non-issue for a localhost dashboard. The control backpressure gap below reinforces the verdict: the two channels need different send policies, which is exactly what two sockets give.
  • gapCorrection from review: the CONTROL stream has no backpressure. The data WS goes through ws-sender; control broadcasts call client.send raw, ignoring bufferedAmount. Health, usage, ingest, lane snapshots, and notifications all share that path, so a suspended or slow dashboard accumulates frames in server memory unbounded. Both fresh-eyes reviewers flagged it. Fix: a small shared control sender with a high-water close or drop-by-message-class rule, mirroring ws-sender.
  • gapNo heartbeat means presence lies. Per-connection focus suppression and the Telegram zero-connections gate both count connections; a half-open socket TCP has not noticed stays counted until timeout. For suppression that fails open (notification delivered anyway), but a zombie connection silently blocks the phone ping, which is the channel of last resort. Review sharpened this: the client's reconnect does not mask it, because the client closes its own socket over the dead path and the server half stays in the presence count; the existing app-level pong is client-initiated and fires only on wake. Protocol ping/pong with a liveness deadline closes it.
  • considerEnvelope versioning. The dashboard is served by the same process, so skew is rare (a long-lived open tab across a server update is the case); a version field that tells an old tab to reload is cheap insurance.

Sources: MDN bufferedAmount, WebSocket heartbeats, reconnection and state sync

2. Session lifecycle state machine

One flat seven-state machine, table-driven, with several out-of-table flags riding beside it.

as built
reference
  • matchesTable-driven and small. Under roughly ten states, an explicit flat table auditable in one screen is the endorsed form; no library needed.
  • considerThe flags are unofficial parallel regions. _gateHeldReady, _titleQuiet, _autoRebasing, and mergeStatus are exactly the "flags shadowing states" smell that statecharts answer with orthogonal regions. The behavior is right today because pure arbiters guard it, but every new flag multiplies the informal cross product. Promoting gate and worktree status to named regions (even as two more small tables) would make the recorder and debug overlay states, not flags. Disposition (2026-08 pass): accepted trade-off, no refactor now. Each flag is owned by a pure arbiter with its own tests (gate-release.js, merge-gate.js, rebase-gate.js, the _titleQuiet reset rules), and a mechanical promotion to region tables changes no behavior. The true flag population is also larger than listed: _sleeping, _autoKilled, _pendingRestart, and _finishing ride the sleep and teardown paths beside the table, which strengthens the finding. Revisit trigger: the next new lifecycle flag, or the first bug traced to a flag cross-product, lands as a named region instead of flag N+1.
  • considerNo supervised restart. A PTY crash lands in terminal FAILED until the operator acts, and only the operator: FAILED flips wasActive false (decideWasActiveFlip in backend.js), so boot auto-resume never revives it. The next-boot revival covers only a Glissa process death, where the flag stays true on disk; the earlier wording overstated it. An OTP-style per-session restart policy (bounded retries, exponential backoff, give up into FAILED) would self-heal transient crashes without recreating a retry loop; the stale-resume-id case already proves the give-up path works. Disposition (2026-08 pass): deferred as a feature, not fixed in docs. Auto-respawning a crashed session (possibly permissionless) is an operator policy call, so it needs an explicit opt-in. Precedent that the plumbing exists: the sleep-kill wake path already auto-restarts (wake() in sessions.js calls restart() when _autoKilled is set), so a supervised policy would reuse that machinery, not invent it.
  • considerUnbounded growth on repeated failures (from the review pass). The session auditLog can append self-transitions past its cap on repeated process_exit_fail. Small bound fix.

Sources: Stately parallel states, Harel statecharts, OTP design principles

3. Signal ingestion and the completion gate

Hooks with no delivery ids, no upstream sequence, and no queryable ground truth, answered with receive-side sequencing, TTLs, and a re-validating release arbiter.

as built
reference
  • matchesThe heuristics are the endorsed fallback. Claude Code hooks carry no delivery id, no sequence, and no queryable task registry. The literature's advice for exactly that case is what Glissa does: stamp a receive-side sequence, treat time only as a bound, re-validate against fresh evidence before acting, and log every decision. The replay harness plus decision trace is textbook event-sourcing-lite.
  • considerFIVE ledgers where one registry would do (count corrected up by review). The first draft said three; verification found the counted map, the declared list, the idle-task-id set, the idle-teammate-name map, and the declared-teammate-id set, driving five distinct expiry rules off three TTL constants. The undercount makes the unification case stronger, not weaker: they are one logical registry (id, kind, status, last evidence) reconciled from several signal families, and collapsing them would turn max(counted, declared) into a query and the expiry rules into one zombie-reaper with per-kind thresholds. Disposition (2026-08 pass): operator agrees the all-agents-done tracking grew overly complex and is open to simplifying if results improve. Two distinct lanes, not to be conflated. Structural: the registry unification above changes no behavior and is the endorsed shape for the next code change in this area (the five stores are confirmed live in sessions.js: _activeAgents, _bgDeclared, _idleTaskIds, _idleTeammateNames, _declaredTeammateIds). Semantic: dropping to orchestrator-only completion already exists as detectBackgroundAgents: false, so an A/B needs zero code; the measure is false COMPLETEs prevented versus stuck-WORKING incidents caused, and both sides are greppable from the recordings' decision traces (kind: 'signal' gate verdicts and decideGateRelease entries). Simplify semantics only on evidence from that comparison, not on complexity distaste alone: every ledger above traces to a live-verified incident.
  • gapThe statusLine-as-heartbeat idea is refuted as first written. The draft assumed the statusLine callback already reached the gate; it does not. It routes only to the usage lane, never to sessions.js, and it is gated on usage.enabled, so a usage toggle would silently change detection. Worse, feeding its timestamps into lastActivitySeq (the naive wiring) makes decideGateRelease return cancel, which DROPS a deferred completion and sticks the card. If pursued at all it must be a separate hold-only gating input, never an activity-sequence feed. Kept here as a documented dead end, not a recommendation.

Sources: Temporal failure detection, Airflow zombie tasks, GitHub webhook practices, Flink watermarks

4. Worktree integration

Eager event-driven rebase with guards and a SHA-pair cooldown; review-gated fast-forward merge back; rerere shared through the common gitdir.

as built
reference
  • matchesEvent-driven rebase and refusal to touch live work. Rebasing on trunk movement rather than at merge time is the merge-train insight, and the dirty/busy/WAITING refusals match "never rewrite under a live agent". rerere sharing via the common gitdir is standard git.
  • priorityOperator priority (2026-08 pass): agents resolve their own integration without intervention. Section is good as built; this priority ranks the considers below and names the one remaining intervention point. rerere replays only a resolution git has already recorded, so the FIRST conflict of each kind still parks and waits on two operator actions: the parked-merge handoff click (pasteMergePrompt over the control WS) and the Enter that sends the pasted prompt, which deliberately ships with no trailing CR. The unattended path is closing that loop: auto-paste, and eventually auto-send, the handoff into the parked worktree's own agent, reusing buildMergePrompt unchanged. Direction recorded, not yet committed to.
  • considerCooldown is time-shaped where the trigger is information-shaped. The documented accepted limitation (a sibling's recorded resolution does not clear the cooldown until a SHA moves) has a merge-queue-style fix: an rr-cache write is the "new information" event, and watching it re-arms the retry immediately instead of eventually. Disposition (2026-08 pass): endorsed, first in line for this section. It serves the unattended priority directly: a sibling's recorded resolution is exactly the event that lets a cooled-down rebase finish with no click, and the watch target (the common gitdir's rr-cache) is one directory.
  • considerNo check gate on the projected result. Merge queues run tests against the candidate as it would land. Running npm test (or the project's check) in the worktree after auto-rebase, surfacing red on the card before the operator clicks Merge, would carry that guarantee without blocking anything. Disposition (2026-08 pass): endorsed as advisory red-on-card, second in line behind the rr-cache watch. It stays advice while the operator clicks Merge; it becomes a load-bearing gate the day the merge click itself is automated, which the unattended priority above makes plausible.

Sources: GitHub merge queue, DORA trunk-based development, git-rerere

5. Notification delivery

In-memory lifecycle entries, defer-not-drop suppression, browser notifications through an open tab, Telegram only at zero connections.

as built
reference
  • matchesDefer-not-drop and presence gating are the right instincts. Suppression that parks instead of discarding, per-connection presence, and gating the phone channel on observed absence all match the published escalation guidance.
  • gapDelivery requires a viewer. No open tab plus Telegram off means a completed session notifies nobody, silently. The standard fix needs no new channel: a service worker with a Push API subscription raises the same native notification with every tab closed. Caveat worth stating: browser push routes through the vendor push service, so it needs internet even for a localhost page; the durable-entry fallback below covers the offline case. Disposition (2026-08 pass): declined. Operator ruling: browser notifications are best-effort and droppable, not a priority; the no-tab case is Telegram's job (the zero-connections gate already fires exactly then, when opted in), so a service worker plus Push API buys reliability on a channel the operator does not need to be reliable. Not pursued.
  • considerEntries are not durable. A server restart loses parked and pending notifications; the state change and its notification are not written together. Persisting entries (one more reason for the single store in section 7) makes delivery survive the crash that most needs reporting. Disposition (2026-08 pass): narrowed by operator ruling. Only notifications that would escalate to Telegram warrant durability; a lost browser notification on restart is acceptable. The right shape is therefore a small durable outbox for pending Telegram pings, not persisting the whole entry store, and this finding stops being an argument for the section 7 single store.
  • considerEscalation stops at delivery. The ladder shape (deliver, wait for ack, escalate) exists in the entry FSM but ends after one channel hop. Optional for a dev tool; the state machine is already shaped for it. Disposition (2026-08 pass): promoted to the section's one endorsed durability investment, per operator ruling that Telegram escalation is the only channel that must not drop. The shape: deliver browser best-effort, wait for ack, escalate an unacknowledged terminal notification to Telegram even while connections are open, feeding the durable outbox above. Prerequisite from section 1: the missing protocol heartbeat, since a zombie connection currently defeats the zero-connections gate and silently blocks exactly this channel.

Sources: transactional outbox, Push API, PagerDuty escalation

6. Poller lanes (PR review, Radar)

setInterval ticks with re-entrancy guards, hard timeouts, concurrency caps, and drain-on-stop.

as built
reference
  • matchesThe poller lifecycle is textbook. Re-entrancy guard, unref'd timer, async stop that drains in-flight work, hard per-job timeouts with aborts, boot-time in-flight reset: this is the full checklist at the lane level. Polling over webhooks is also correct here; a local tool has no public ingress.
  • gapCorrection from review: shutdown does not await those drains. The lanes expose async stop(), but backend.js shutdown fires void packService.stop(), void usage.stop(), void packDistiller.stop(), void memoryStore.stop() without awaiting, and server-lifecycle awaits only PTY reaps. A restart during a PR review or a Radar fix can start a fresh backend while the old lane is still discarding a worktree or writing state. Two reviewers converged on this independently and named it the biggest systemic risk: lifecycle finality, not the state machine. Fix: make shutdown await every lane stop promise. Disposition (2026-08 pass): agreed it must be handled, and extracted as its own workstream rather than folded into poller-lane tweaks; the unawaited calls above were re-confirmed live in this pass. The shape when it lands: a shutdown coordinator in server-lifecycle.js holding a registry of async stoppers, awaited with a bounded Promise.allSettled alongside the existing 3000ms PTY reap bound, so one stalled lane cannot hang exit. Same workstream (from the review pass): a lane timeout-abort can resolve the job promise before the PTY reaps, racing worktree cleanup; the coordinator should await the reap before discard.
  • gapCorrection from review: durable writes on hot paths are synchronous. Config, PR-state, and Radar-state writes use sync filesystem calls on the one shared event loop, so a stalling write blocks hook replies, PTY streaming, and control traffic. The SQLite move below also fixes this (WAL writes off the whole-file-rewrite path), or queue async writers for recurring state and keep sync only for boot and CLI.
  • considerErrors deserve backoff. A gh or PostHog outage is re-polled at full cadence. Full-jitter exponential backoff plus honoring Retry-After is a small change to the shared lane-runner and covers every lane at once.
  • considerETags are free. If-None-Match makes an unchanged PR list cost zero rate limit. Minor at one operator's volume; cheap in the shared gh wrapper.

Sources: GitHub REST best practices, AWS backoff and jitter

7. Durable state

Roughly ten sidecar JSON files beside the config, each with its own atomic-write, locking, and reload conventions.

as built
reference
  • matchesThe per-file discipline is careful. tmp+rename everywhere, deliberate corruption policies (auth fails closed, budgets fail noisy), and the complete-pass-only warehouse write are all sound choices within the files-as-store frame.
  • gapConfig self-write suppression is time-shaped (from the review pass). Any config event within 500 ms of a Glissa save is ignored, so a fast hand-edit right after a hook persist is silently dropped until the next edit. Fix: suppress by written-content signature, not a time window.
  • considerThe frame itself is the finding. SQLite's own documentation makes the case: one WAL-mode database replaces N independent write paths, gives cross-key transactions (the lane ledger and budget state cannot disagree after a crash), removes the O_EXCL lockfile machinery under pairings.json, and turns the warehouse's whole-file rewrite into row upserts. node:sqlite ships in Node 24, so this violates no dependency rule. Keep config.json (hand-edited) and recordings (append-only forensics) as files; those are exactly the documented exceptions. Disposition (2026-08 pass): operator is open to a database, gated on a serious dedicated design pass over the shape; no incremental adoption. Constraints recorded: node:sqlite only (in Node 24 already, zero new dependencies), and nothing bloated on the machines that run Glissa: one file beside config.json, no server process, no migration framework. The shape question is real because the repo already holds a second candidate: the Visions memory plan (docs/plan-visions-3.md, and the operator's Visions doc at claude.ai/code/artifact/f7cbafd9) chose files as source of truth with an optional, rebuildable, deletable SQLite FTS5 index as a derived cache. The design pass must reconcile the two shapes machine-wide: SQLite-primary for operational sidecar state versus files-primary with derived indexes, with Visions counted as a first-class future tenant so the answer is chosen once, not per feature.
  • gapNo cross-file recovery point. A crash between two sidecar writes leaves the set mutually inconsistent with no way to notice; each file recovers alone. This is the concrete failure the transactional store closes, and it is also what makes the notification outbox in section 5 possible. Disposition (2026-08 pass): folded into the store design pass above as its primary requirement; whichever shape wins must give a cross-key recovery point for the state that has to agree after a crash (lane ledger with budget state, pairing writes), and the section 5 outbox rides the same decision.

Sources: SQLite as application file format, SQLite WAL

8. Context mill (full pipeline)

Expanded at operator request (2026-08 pass) from watchers-only to the whole mill, for clarification. The review verdicts below still cover the rebuild loop specifically; the pipeline walk is descriptive, sourced from AGENTS.md and the module docs.

The mill end to end. A pack is versioned, token-budgeted local context delivered to sessions with --add-dir. The stages:

  1. Author. Specs (packs/specs/<name>.pack.json, filename matches the name field) and shared source material (packs/sources/**) are version-controlled with Glissa; relative patterns resolve against packs/, so a spec reads the same from a checkout or a global install. Sources are local files only, a deliberate trust boundary: pack bytes land in permissionless sessions.
  2. Distill (opt-in). server/pack-distiller.js (gated by config.packDistiller) runs headless claude -p sessions that regenerate derived files under packs/ when their stamped source hashes drift; each derived file carries a glissa-distill v1 stamp, each run accepts only a result-file verdict of DISTILLED, NO_CHANGE, or ERROR. It writes files, nothing more: the watcher below sees the write, so distiller and builder compose with no direct coupling.
  3. Plan (pure). server/core/pack-core.js holds every decision: strict spec validation (unknown keys are errors), the glob matcher, the chars/4 token estimate (named tokenEstimateMethod in the manifest so nobody mistakes it for a tokenizer), and planPackBuild returning the output file map plus manifest. Deterministic by contract: same spec plus same content yields byte-identical output; the version hashes every DELIVERED file, manifest excluded since it carries builtAt. Budgets are hard gates (budgetTokens whole-pack, a tighter cap on the always-loaded CLAUDE.md index), and a pattern matching no file is a build error, never a silent hole.
  4. Build and publish. server/pack-builder.js walks async (skipping .git, node_modules, every symlink), publishes into a tmp sibling under ~/.glissa/packs/built/<name>/, rotates current/ to previous/, renames the tmp in. A failed build leaves the last good current/ untouched; a build whose version already matches writes nothing (unchanged: true), which both makes the loops cheap and avoids poking live sessions that hot-reload skills from the delivered dir.
  5. Rebuild automatically. Two loops in server/pack-service.js (IO-free, injected deps): per-spec recursive debounced watchers on each source root for latency, and a re-entrancy-guarded 15 minute sweep for correctness (covers dropped events, roots that did not exist at boot, spec-file edits, platforms without recursive watch). Every rebuild runs through one promise chain. Kill switch packsAutoRebuild. This stage is what the verdicts below review.
  6. Announce. A published rebuild broadcasts pack-updated on the control WS; the connect snapshot carries packVersions. A card whose delivered version differs shows the stale chip (pack-stale-core.mjs). pack-updated is deliberately not in control replay retention: the snapshot repairs the map.
  7. Deliver at spawn. A project record's hand-edited packs list (deliberately not control-WS settable) resolves through resolveBuiltPack; one --add-dir per resolved pack, delivered { name, version } stamped on the snapshot. CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 is set only when a dir was added (without it Claude Code loads skills but not the pack's CLAUDE.md or rules). An unbuilt or unreadable pack is SKIPPED with a decision-trace entry, never a blocked spawn. The ephemeral PR-review and Radar lanes consume packs through the same normalization.
  8. Notify live sessions. A rebuild reaches a running session only halfway (skills hot-reload, CLAUDE.md and rules do not), so when pack-updated names a pack a session spawned against, the next accepted UserPromptSubmit reply carries a Glissa-authored staleness notice via additionalContext: pack name and versions plus fixed guidance, never a byte of pack content, hard-capped, consumed on read, re-armed only by a newer version.
  9. Measure consumption. Pack-carrying sessions get a matcher-scoped PostToolUse Read hook; pack-read-tracker.js classifies reads against delivered pack dirs (shape-based path normalization). Counts ride the snapshot, readsSinceNotice shows whether a notice produced re-reads, and the recording footer aggregates (packReads) instead of drowning the signal stream. Pair with the usage lane for the cost side of pack-on versus pack-off.
as built
reference
  • matchesWatcher-for-latency, sweep-for-correctness is exactly the published pattern, as are ignore-before-register (the @parcel/watcher choice), serialized builds, and skip-identical-version publishes.
  • gapPublish rotation has a crash window (from the review pass). The current/ to previous/ rotation is two renames, so a crash between them can leave no current/ at all; "atomic publish" overstates it. Fix: rename tmp over a sidelined current (single visible swap), or tolerate a missing current/ by falling back to previous/ at resolve time.
  • considerMid-write reads. An editor save emits events before the bytes settle; hashing a half-written file publishes a version that immediately re-publishes. Self-healing (the next event or sweep fixes it), but a size-stability wait before hashing removes the flap.
  • considerDebounce needs a ceiling. A trailing-only debounce under continuous churn defers forever; the sweep bounds it at 15 minutes. A max-wait on the debounce itself would bound it at seconds.

Sources: chokidar (awaitWriteFinish), fs.watch caveats

9. Localhost and remote security

Loopback bind, Origin allow-list, per-session hook tokens, listener-port trust, hashed single-use pairing.

as built
reference
  • matchesMost of the reference is already here. Listener-port trust (endorsed over IP/header trust), Origin allow-listing, refusing wider binds without an explicit flag, hashed single-use pairing with TTL, and keeping remote config off the settable-keys list are all current practice.
  • priorityOperator ruling (2026-08 pass): section accepted as written, and security is to be taken up a notch. Every finding below is accepted as a prioritized hardening workstream, not backlog. Order when it lands: the any-port Origin gap first (port-exact allow plus refusing an absent Origin, since it is the RCE-grade one), the /pair/ path normalization second, the 0600/0700 hook settings file third, and the local control-WS token fourth, as the added defense layer the Origin fix argues for. Host validation rides along as the cheap defense-in-depth line in the same slice.
  • closedHost header validation. Closed by server/core/host-policy.js: an Express middleware ahead of the remote gate, plus the same check on the upgrade path, refuses a Host that is neither a loopback literal (with any port) nor the remote listener's public host or an allow-listed origin's host. An ABSENT Host still passes: rebinding always carries a name, so refusing it would only break HTTP/1.0 clients. Defense in depth as the review said, not the missing lock.
  • closedOrigin allows any localhost PORT, and a missing Origin outright. Closed by server/core/origin-policy.js: a loopback origin is now admitted only on a LISTENER port (the port the socket actually landed on, so nothing a client sends decides it), and a mismatch falls through to the allow-list rather than refusing, so an explicitly configured local proxy origin still wins. A missing Origin is refused on the dashboard channels (control, data) via requireOrigin; the HTTP ingresses and the Visions editor relay keep accepting one, since those clients are not browsers.
  • closedRemote-auth path guard is bypassable by an un-normalized /pair/ prefix. Closed by normalizePathname in server/core/request-trust.js: the pathname is decoded once (matching express) before the prefix check, and any dot segment, surviving %2e, or decode failure comes back suspicious, which isPairPath refuses outright. The reviewer's reproduction is pinned in tests/backend-remote-enabled.test.js against the live remote listener.
  • closedHook settings file (with its bearer token) is world-readable in shared /tmp on POSIX hosts. Closed by detection/settings-injector.js: directories are created and re-chmodded 0700, the file 0600 (chmod after write, since a mode option only applies to a file the call creates), and the base dir must prove it is a real directory owned by this user before anything is written under it, so a pre-created path or a symlink standing in for one is a refusal rather than an arbitrary-file write.
  • closedThe tokenless control WS. Closed by a per-process page token: minted at boot, handed to the page over same-origin GET /control-token (a cross-origin fetch is refused outright rather than relying on the browser to withhold the body), and required on both the control and data upgrades from a local client. A paired REMOTE device is exempt: its credential is the pairing cookie, and that path is unchanged. The accepted tradeoff shrinks back to what it always claimed to be, any local PROCESS, no longer any local web PAGE.

Sources: GitHub: localhost dangers, CSWSH, Chrome Local Network Access
