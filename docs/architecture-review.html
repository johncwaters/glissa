Glissa Architecture Review

Each subsystem of Glissa compared against the established pattern for its problem class: event handling, pollers, webhook-grade signal ingestion, completion detection, notification delivery, state machines, local persistence, branch integration, and localhost security. The left diagram is what is built; the right is the reference shape from current practice. Verdicts are honest both ways: several Glissa designs already match the canon, and several "correct" patterns would be overkill for a single-process, single-operator tool. Sources are linked per section.

VerdictMeaning
matchesAlready the best-practice shape, or a deliberate documented tradeoff that current practice endorses for this context.
considerA named pattern would improve robustness or simplicity; not broken today.
gapA real hole with a concrete failure mode the reference pattern closes.

1. Transport and fan-out

Two WebSockets plus HTTP ingresses, with backpressure on the byte stream and a replay log on the control stream.

as built
reference
  • matchesBackpressure and replay retention are canonical. bufferedAmount gating on the byte stream, and a control replay log that retains only message types the connect snapshot cannot reconstruct, are exactly the published guidance.
  • gapNo heartbeat means presence lies. Per-connection focus suppression and the Telegram zero-connections gate both count connections; a half-open socket TCP has not noticed stays counted until timeout. For suppression that fails open (notification delivered anyway), but a zombie connection silently blocks the phone ping, which is the channel of last resort. Protocol ping/pong with a liveness deadline closes it.
  • considerEnvelope versioning. The dashboard is served by the same process, so skew is rare (a long-lived open tab across a server update is the case); a version field that tells an old tab to reload is cheap insurance.

Sources: MDN bufferedAmount, WebSocket heartbeats, reconnection and state sync

2. Session lifecycle state machine

One flat seven-state machine, table-driven, with several out-of-table flags riding beside it.

as built
reference
  • matchesTable-driven and small. Under roughly ten states, an explicit flat table auditable in one screen is the endorsed form; no library needed.
  • considerThe flags are unofficial parallel regions. _gateHeldReady, _titleQuiet, _autoRebasing, and mergeStatus are exactly the "flags shadowing states" smell that statecharts answer with orthogonal regions. The behavior is right today because pure arbiters guard it, but every new flag multiplies the informal cross product. Promoting gate and worktree status to named regions (even as two more small tables) would make the recorder and debug overlay states, not flags.
  • considerNo supervised restart. A PTY crash lands in terminal FAILED until the operator acts or the next boot. An OTP-style per-session restart policy (bounded retries, exponential backoff, give up into FAILED) would self-heal transient crashes without recreating a retry loop; the stale-resume-id case already proves the give-up path works.

Sources: Stately parallel states, Harel statecharts, OTP design principles

3. Signal ingestion and the completion gate

Hooks with no delivery ids, no upstream sequence, and no queryable ground truth, answered with receive-side sequencing, TTLs, and a re-validating release arbiter.

as built
reference
  • matchesThe heuristics are the endorsed fallback. Claude Code hooks carry no delivery id, no sequence, and no queryable task registry. The literature's advice for exactly that case is what Glissa does: stamp a receive-side sequence, treat time only as a bound, re-validate against fresh evidence before acting, and log every decision. The replay harness plus decision trace is textbook event-sourcing-lite.
  • considerThree ledgers where one registry would do. The counted map, declared list, and idle name set are one logical registry (id, kind, status, last evidence) reconciled from three signal families. Unifying them would collapse four TTL classes into one zombie-reaper rule with per-kind thresholds and make max(counted, declared) a query instead of a formula.
  • considerA heartbeat already exists and is not used for liveness. The statusLine callback fires per assistant/tool step during a live turn. Feeding its arrival times into the gate as a liveness signal (Temporal's heartbeat-vs-timeout split) would shrink dependence on the fixed quiet window: a turn that is visibly stepping cannot be complete. Limits: it never fires while idle or in headless sessions, so it can only hold a gate closed, never open one.

Sources: Temporal failure detection, Airflow zombie tasks, GitHub webhook practices, Flink watermarks

4. Worktree integration

Eager event-driven rebase with guards and a SHA-pair cooldown; review-gated fast-forward merge back; rerere shared through the common gitdir.

as built
reference
  • matchesEvent-driven rebase and refusal to touch live work. Rebasing on trunk movement rather than at merge time is the merge-train insight, and the dirty/busy/WAITING refusals match "never rewrite under a live agent". rerere sharing via the common gitdir is standard git.
  • considerCooldown is time-shaped where the trigger is information-shaped. The documented accepted limitation (a sibling's recorded resolution does not clear the cooldown until a SHA moves) has a merge-queue-style fix: an rr-cache write is the "new information" event, and watching it re-arms the retry immediately instead of eventually.
  • considerNo check gate on the projected result. Merge queues run tests against the candidate as it would land. Running npm test (or the project's check) in the worktree after auto-rebase, surfacing red on the card before the operator clicks Merge, would carry that guarantee without blocking anything.

Sources: GitHub merge queue, DORA trunk-based development, git-rerere

5. Notification delivery

In-memory lifecycle entries, defer-not-drop suppression, browser notifications through an open tab, Telegram only at zero connections.

as built
reference
  • matchesDefer-not-drop and presence gating are the right instincts. Suppression that parks instead of discarding, per-connection presence, and gating the phone channel on observed absence all match the published escalation guidance.
  • gapDelivery requires a viewer. No open tab plus Telegram off means a completed session notifies nobody, silently. The standard fix needs no new channel: a service worker with a Push API subscription raises the same native notification with every tab closed. Caveat worth stating: browser push routes through the vendor push service, so it needs internet even for a localhost page; the durable-entry fallback below covers the offline case.
  • considerEntries are not durable. A server restart loses parked and pending notifications; the state change and its notification are not written together. Persisting entries (one more reason for the single store in section 7) makes delivery survive the crash that most needs reporting.
  • considerEscalation stops at delivery. The ladder shape (deliver, wait for ack, escalate) exists in the entry FSM but ends after one channel hop. Optional for a dev tool; the state machine is already shaped for it.

Sources: transactional outbox, Push API, PagerDuty escalation

6. Poller lanes (PR review, Radar)

setInterval ticks with re-entrancy guards, hard timeouts, concurrency caps, and drain-on-stop.

as built
reference
  • matchesThe lifecycle is textbook. Re-entrancy guard, unref'd timer, async stop that drains in-flight work, hard per-job timeouts with aborts, boot-time in-flight reset: this is the full checklist. Polling over webhooks is also correct here; a local tool has no public ingress.
  • considerErrors deserve backoff. A gh or PostHog outage is re-polled at full cadence. Full-jitter exponential backoff plus honoring Retry-After is a small change to the shared lane-runner and covers every lane at once.
  • considerETags are free. If-None-Match makes an unchanged PR list cost zero rate limit. Minor at one operator's volume; cheap in the shared gh wrapper.

Sources: GitHub REST best practices, AWS backoff and jitter

7. Durable state

Roughly ten sidecar JSON files beside the config, each with its own atomic-write, locking, and reload conventions.

as built
reference
  • matchesThe per-file discipline is careful. tmp+rename everywhere, deliberate corruption policies (auth fails closed, budgets fail noisy), and the complete-pass-only warehouse write are all sound choices within the files-as-store frame.
  • considerThe frame itself is the finding. SQLite's own documentation makes the case: one WAL-mode database replaces N independent write paths, gives cross-key transactions (the lane ledger and budget state cannot disagree after a crash), removes the O_EXCL lockfile machinery under pairings.json, and turns the warehouse's whole-file rewrite into row upserts. node:sqlite ships in Node 24, so this violates no dependency rule. Keep config.json (hand-edited) and recordings (append-only forensics) as files; those are exactly the documented exceptions.
  • gapNo cross-file recovery point. A crash between two sidecar writes leaves the set mutually inconsistent with no way to notice; each file recovers alone. This is the concrete failure the transactional store closes, and it is also what makes the notification outbox in section 5 possible.

Sources: SQLite as application file format, SQLite WAL

8. Context mill watchers

Per-root debounced watchers for latency, a fifteen-minute sweep for correctness, content-hash versioning, atomic publish.

as built
reference
  • matchesWatcher-for-latency, sweep-for-correctness is exactly the published pattern, as are ignore-before-register (the @parcel/watcher choice), serialized builds, and skip-identical-version publishes.
  • considerMid-write reads. An editor save emits events before the bytes settle; hashing a half-written file publishes a version that immediately re-publishes. Self-healing (the next event or sweep fixes it), but a size-stability wait before hashing removes the flap.
  • considerDebounce needs a ceiling. A trailing-only debounce under continuous churn defers forever; the sweep bounds it at 15 minutes. A max-wait on the debounce itself would bound it at seconds.

Sources: chokidar (awaitWriteFinish), fs.watch caveats

9. Localhost and remote security

Loopback bind, Origin allow-list, per-session hook tokens, listener-port trust, hashed single-use pairing.

as built
reference
  • matchesMost of the reference is already here. Listener-port trust (endorsed over IP/header trust), Origin allow-listing, refusing wider binds without an explicit flag, hashed single-use pairing with TTL, and keeping remote config off the settable-keys list are all current practice.
  • gapNo Host header validation. DNS rebinding makes an attacker's domain resolve to 127.0.0.1; the browser then treats the local server as same-origin, and the Origin header on plain HTTP requests can be absent. An allow-list of localhost/loopback literals on both listeners is a few lines in the request-trust core and closes the classic localhost-daemon attack.
  • considerThe tokenless control WS is documented, but the bar has moved. "Any local process can spawn a permissionless session" is accepted in AGENTS.md; the published guidance now treats a local unguessable token as the third layer even on single-user machines, because the control channel is RCE-grade. The dashboard is served by the same process, so it can receive the token with the page; cost is small.

Sources: GitHub: localhost dangers, CSWSH, Chrome Local Network Access

The strongest overall property is one the reference patterns only approximate: nearly every decision in Glissa is a pure function with a recorded verdict and a replay harness behind it. Most of the gaps above are delivery-layer and durability concerns around that core, not flaws in it.
