# glissa

## Purpose
Glissa is a lightweight Node.js background process that spawns and manages Claude Code sessions via node-pty, streams terminal output to a browser dashboard over WebSockets, derives session status from structural signals (Claude Code hooks plus an OSC-0 title fallback, never screen scraping), and notifies the operator through browser notifications.

## For AI Agents

### Working In This Directory
- Server code is CommonJS only (`require` / `module.exports`); frontend is ESM bundled by Vite. Node >=18 (developed on v24), Windows 11.
- Do NOT add dependencies without explicit instruction.
- Status detection is structural (hooks + OSC-0 title). Never reintroduce PTY body/content scraping.
- Spawn sessions with `pty.spawn` (never `child_process.spawn`), no `shell: true`; scrub env via `session/core/spawn-env.js`.
- All sessions share one Node event loop: no sync git/fs on recurring paths (polls, turn-end, watchers); use async `execFile` with yields. One-shot cold paths may stay sync.
- Localhost-only trust boundary: never bind `0.0.0.0`; keep the per-session bearer token check on `POST /hook/:glissaId/:event`.
- House style: no literal em dash, en dash, ellipsis character, or emoji anywhere (source, tests, docs, commits). When code must emit such a character, build it via `String.fromCharCode`.
- Avoid `else`: prefer early returns and guard clauses.
- Prefer the seam pattern: pure logic in `session/core/` or `*-core.mjs` modules, thin IO shells around them.
- Inter-module communication via Node `EventEmitter`, not globals or direct coupling.
- Sessions are keyed by stable UUID `id`; `name` is display-only.

### Testing Requirements
- Run `npm test` (node:test based suite in `tests/`) before claiming completion.
- New pure logic gets a unit test in `tests/`; detection changes should also pass the replay harness fixtures.

### Common Patterns
- Resolve-then-branch spawn: `claude` resolved once at module load; `.exe` spawned directly, `.cmd`/`.bat`/`.ps1` shims fall back to `cmd.exe /c claude`.
- Dual WebSocket: data WS (`/terminals/:sessionId`, raw PTY bytes) and control WS (`/control`, JSON messages).
- Table-driven state machines (`session/core/state-machine.js`, `shared/notification-states.js`) with explicit transitions.

## Dependencies

### External
- `express` - HTTP server and static file serving
- `ws` - WebSocket server (no Socket.IO, ever)
- `node-pty` - Pseudo-terminal for spawning Claude Code with real PTY support (requires VS Build Tools on Windows)
- `@parcel/watcher` - Recursive filesystem watcher for the fs ingest source only (`server/ingest-fs.js`). Applies ignores BEFORE watch registration, which is what keeps a `node_modules` tree from exhausting `fs.inotify.max_user_watches` on Linux; ships 12 platform prebuilds as optionalDependencies plus a wasm fallback, so no compile step in practice. A load failure disables that one source with a warning and nothing else. See `docs/plan-ingestion.md`, "File watching"
- `@xterm/xterm` - Terminal emulator (loaded in browser via ES modules, not in Node.js)
- `@xterm/addon-fit` - xterm.js addon for fitting terminal to container (browser only)
- `@xterm/addon-webgl` - xterm.js addon for WebGL rendering (browser only)

### Dev Dependencies
- `vite` - Frontend build tool (dev server with HMR, production bundling)
- `tailwindcss` - Utility-first CSS framework (v4)
- `@tailwindcss/vite` - Tailwind CSS Vite plugin

**Notes:**

- `node-pty` requires C++ build tools (Visual Studio Build Tools on Windows)
- `@xterm/*` packages are bundled by Vite for the browser, not loaded directly in Node.js

## Development Workflow

- `npm run dev` - Vite dev server with HMR on port 5173, Express + WebSocket backend attached via plugin (single process)
- `npm run dev:server-only` - Express backend only on port 3000 (for debugging backend without Vite)
- `npm run build` - Production build to `dist/`
- `npm start` - Production server (serves from `dist/` if it exists, otherwise `public/`)
- `npm run preview` - Preview production build via Vite

## Platform and Runtime

- **OS:** Windows 11
- **Node:** v24+
- **Module system:** CommonJS (`require` / `module.exports`) for server - no ESM. Frontend uses ES modules bundled by Vite.

## Key Design Decisions

### Inter-module Communication

Use Node.js `EventEmitter` for communication between modules. Do not use global variables or direct coupling.

### Session State Machine

Sessions follow a 7-state machine implemented in plain JS:

```
INITIALIZING → STARTING → RUNNING → WAITING → IDLE → DONE
                                                    ↘ FAILED
```

States are string constants. Transitions are explicit - no implicit state mutation.

### Status Detection (structural signals - NOT screen scraping)

Status is derived from machine-emitted signals, never from parsing the rendered TUI:

- **Authoritative: Claude Code hooks.** At spawn, `sessions.js` appends `--settings <file>` (written by `detection/settings-injector.js`) injecting HTTP hooks (`Stop`, `Notification`, `UserPromptSubmit`, `SessionStart`/`End`, `SubagentStart`/`SubagentStop`) that POST to `POST /hook/:glissaId/:event` on the existing Express server. A per-session bearer token (in the hook URL) is validated by `detection/hook-source.js` `HookRouter`. No target-repo modification; HTTP hooks need no shell.
- **Fallback: OSC-0 title** (`detection/osc-title-source.js`) - braille or circle-halves spinner = `working`, idle glyph = `ready`; an unknown glyph is `unknown`, never a guess. It NEVER emits `awaiting-input`.
- `detection/status-source.js` merges both (precedence hook > title), holds `ready` for a conflict window so a racing `awaiting-input` wins, and dedups. `working`/`resume` arriving inside that window CANCEL the held `ready` (the turn did not settle; letting it resolve fired a false COMPLETE right after a fast re-prompt). `sessions.js._onStatus` maps the normalized signal to a transition per the signal x state matrix (see `docs/postmortem-terminal-detection.md` for the design rationale and live-verification findings).
- **idle_prompt is demoted.** A `Notification(idle_prompt)` maps to `ready` but with `confidence: 'low'` (`mapHookConfidence` in `hook-source.js`): an idle nudge means "Claude is waiting for YOU", so it may only confirm quiescence from RUNNING, same as the title fallback. It must never complete a fresh IDLE session or a WAITING prompt.
- **/clear and /compact are quiet.** They fire `SessionEnd`+`SessionStart(source: clear|compact)` (no `UserPromptSubmit`, no `Stop`), but the TUI redraw flashes a spinner+idle glyph in the OSC title, which used to open a fake work cycle and fire a false "finished working" per /clear. On `SessionStart(source: clear|compact)` the session resets both sources (cancelling any held `ready`) and latches title signals off (`_titleQuiet`) until the next real `UserPromptSubmit`.
- **Background sub-agents (completion gate).** `SubagentStart`/`SubagentStop` (each carrying `agent_id`) are NOT transitions. `sessions.js` keeps a per-session live `agent_id` set (pure bookkeeping in `session/core/agent-tracker.js`), and `mapSignalToEvent` suppresses `ready` to `task_complete` while that set is non-empty, so a main-agent `Stop` fired while a background sub-agent (Task `run_in_background` / Ctrl+B) is still running does NOT falsely COMPLETE the card. The main agent usually auto-resumes when the sub-agent finishes and its later `Stop` (count back to 0) completes normally; when no later `Stop` ever comes (idle teammate, dropped `SubagentStop`), the suppressed `ready` is HELD (`_gateHeldReady` in `sessions.js`) and released when the count drains (via `SubagentStop`, a declared 0, or the TTL prune, bounded by a one-shot release timer), so the card cannot pin WORKING forever. The hold is cancelled by any newer activity (`working`/`resume`/`awaiting-input`), any state change, /clear, or PTY exit/restart. The live count rides `toSnapshot().activeAgents` and a `session-agents` control broadcast (rendered as an "N agents" card chip). On by default; `config.json` `detectBackgroundAgents: false` is the kill switch (signals ignored, behavior as before). A dropped `SubagentStop` is bounded by a per-id TTL prune (`session/core/agent-tracker.js`) plus a hard clear on PTY exit / restart. **Authoritative override:** `Stop`/`SubagentStop` payloads carry `background_tasks` (Claude Code v2.1.145+), which sees background work the Start/Stop counting cannot (background Bash tasks, native-team teammates). Ground truth (extracted from the CC 2.1.199 binary, memory: background-tasks-ground-truth): the field is an ARRAY of `{ id, type, status, ... }` pre-filtered by the emitter to running|pending entries; `agent-tracker.extractBackgroundTasks` parses that shape only (the `{ count, tasks }` object from claude-code#33310 is a statusLine surface, never sent to hooks) with a defensive settled-status deny-list. `sessions.js` keeps the declared entries (`_bgDeclared`) and takes `max(counted, declaredActive)` for the gate, drains the counted map when a payload declares 0 running (no waiting on the TTL), and clears the snapshot on `resume` / PTY exit / restart. Absent field (older Claude) = counting behavior unchanged. **Teammate/task lifecycle drains:** an idle-but-alive teammate stays `status: running` in Claude's registry until shutdown, so every Stop re-declares it; Glissa subscribes `TaskCreated`/`TaskCompleted`/`TeammateIdle` (tracking-only, `_trackTaskLifecycle`) to drain per-id: `TaskCompleted(task_id)` adds the id to `_idleTaskIds`, which filters declared entries out of the gate and survives `resume`; `TaskCreated` reactivates the id (and, like `SubagentStart`, invalidates a gate-held ready). `TeammateIdle(teammate_name)` is recorded BY NAME, with no per-id resolution path at all: `TaskCreated` NEVER fires for named-Agent teammates (live-verified vs CC 2.1.200, memory: named-agent-teammate-hook-sequence), and a declared entry can NOT be matched to a name (its `description` is the spawn prompt, live-verified), so a name-to-id map would be dead bookkeeping. The idle name goes in `_idleTeammateNames` (Map<name, ts>, persists across `resume`), and `agent-tracker.declaredActiveCount` takes a fifth `idleNameCount` argument: it subtracts that count from the surviving declared `teammate`-type entries, clamped to that teammate count so a stale/extra idle name can never mask a shell/subagent entry. This is count-based, not id-based, so N simultaneous idle teammates each drain the gate by one regardless of ambiguity. A name is re-gated (deleted from `_idleTeammateNames`) by a matching `TaskCreated`, or by a `SubagentStart` whose `agent_id` embeds the name (`a<name>-<hex>`, live-captured) since no `TaskCreated` ever fires for a teammate the lead re-wakes via mailbox. **Releasing a held ready is re-validated against live evidence, never against the count alone.** One pure arbiter, `session/core/gate-release.js decideGateRelease`, decides every hold: `cancel` (the state moved on, or a non-ready signal arrived AFTER the stash), `gated` (background work still live), `wait` (eligible, quiet window not elapsed) or `release`. `sessions.js _evaluateGateHeldReady` is the thin shell that acts on the verdict and re-arms the single gate timer; there is no separate eager-clear path deciding staleness in parallel. Staleness is ordered by a signal SEQUENCE number, not a clock, because signals routinely share a millisecond. The activity check exists because a lead that auto-resumes on a teammate mailbox message fires no `UserPromptSubmit` and, since `OscTitleSource` emits `working` only on a kind EDGE, a card RUNNING with an already-spinning title reported nothing either: a held Stop then released minutes into a NEW turn and falsely COMPLETEd a working card. `_stashGateHeldReady` therefore also calls `resyncWorkingLatch()` on the title source, so the next real spinner frame proves the turn is still open (a genuinely finished turn emits no further frames, so the release path is unaffected). The `gateReleaseSettleMs` quiet window (default 10s, `DEFAULT_GATE_RELEASE_SETTLE_MS` in `gate-release.js`) is still needed on top of that: the drain usually lands 1-3s BEFORE the mailbox wake, so an instant release would fire a false COMPLETE + notification before any spinner frame could arrive. That window is measured from the evaluation that FIRST OBSERVES the drain (`_gateQuietSince` is null while the gate is still gating, and is stamped by the first evaluation that sees zero background work), never from the last still-gated evaluation alone: gate evaluations are event/TTL driven, so a hold gated for minutes reaches the drain with a stale quiet timestamp, and trusting it released instantly and falsely COMPLETEd a card whose lead resumed on the teammate's mailbox message 8.5s after the SubagentStop drain (incident 2026-08-14; regression tests in `tests/sessions-detection.test.js`). Explicit `_clearGateHeldReady` calls remain only where no signal ever reaches `_onStatus` to carry the evidence: `SubagentStart`/`TaskCreated` (tracking-only signals, and fresh background work invalidates an older Stop), `SessionStart(clear|compact)`, the `resume` branch (it must beat the `_clearBgDeclared` drain in the same call), and PTY start/exit/destroy. A genuinely settled idle teammate still completes the card in ~10s instead of at the TTL. `_idleTeammateNames` is TTL-pruned lazily in `_activeAgentCount` (bound by `agentTtlMs`) so a stale name can never mask a future same-named teammate forever. **Scheduled self-revival never gates:** a declared entry of `type: 'dream'` (a pending `ScheduleWakeup`) is skipped entirely by `declaredActiveCount` (`NON_GATING_TASK_TYPES` in `agent-tracker.js`) - per `session/core/wakeup-tracker.js`'s own design a Stop with a pending wakeup IS a finished turn, surfaced via the advisory wakeup chip, not the completion gate. **Hook-less task types:** declared `shell`/`monitor` entries never get ANY completion hook, so past `shellTaskTtlMs` (default 5 min) since the declaring Stop they stop counting (`WEAK_TASK_TYPES` in `agent-tracker.js`) and the held-ready release timer re-checks at `min(agentTtlMs, shellTaskTtlMs, teammateTaskTtlMs)`; without this a background dev server or orphaned test shell pinned the card WORKING for the full 30-minute agent TTL after every turn. **Declared teammate entries are also TTL-bounded** (`teammateTaskTtlMs`, default 90s): real teammate work is already covered by the counted `SubagentStart`/`SubagentStop` map, so a declared `teammate` entry only matters for a dropped `SubagentStart`, while an idle-but-alive teammate is declared running forever and its drain depends on `TeammateIdle`/`TaskCompleted` hooks that sometimes never arrive; a short TTL bounds that stuck-WORKING failure at seconds instead of the 30-minute agent TTL.
- The PTY data path does NO content parsing beyond scanning for OSC-0 titles. Do not reintroduce body/line scraping.

#### rtk Output Compression

`config.rtk` is an opt-in top-level boolean. When enabled and an rtk binary resolves, Glissa injects rtk's `PreToolUse` Bash hook through the per-session managed `--settings` file. Glissa never edits `~/.claude` and never runs `rtk init`. The matcher is Bash only, so PowerShell-tool calls and built-in Read/Grep/Glob traffic are not compressed. Split-pane teammates are unverified.
The hook command is written with forward slashes because Claude Code executes command hooks via git-bash on Windows; only drive-letter install paths are supported (a UNC `\\server\...` rtk path is not). The spawn env prepends the rtk binary's directory to PATH so rtk's bare `rtk <cmd>` rewrites resolve.

### Notifications (lifecycle + delivery)

- The backend `state-change` listener acknowledges the old entry BEFORE deciding/triggering the new one (a WAITING -> COMPLETE hop must deliver the completion, not land on a live DELIVERED entry). The per-state decision is `session/core/notify-gate.js decideNotification(to, gate, event, { signal, hookSeen })`: terminal categories fire once per work cycle, and `user_kill` is always silent (killing a session is not "finished working"). **A work cycle starts only on a USER-driven RUNNING entry** - `INITIALIZING` (restart), event `user_input` (the user answered a WAITING prompt), or signal `resume` (an authoritative `UserPromptSubmit`). A self-wake RUNNING entry (title `working` after an orchestrator lead auto-resumes on a teammate mailbox message, which fires no `UserPromptSubmit`) does NOT reset the cycle, so a lead that wakes N times per prompt can fire 'complete' at most once per prompt instead of once per orchestration round. A degraded title-only session (`hookSeen: false`, and omitted opts) keeps the legacy reset-on-every-RUNNING behavior since it has no resume signal to key off. Because `working` (title) and `resume` (hook) are both IMMEDIATE in `status-source.js`, the title spinner can win the IDLE/COMPLETE->RUNNING transition and carry signal `working` for a REAL user prompt; the session therefore also emits a dedicated `user-prompt` event from the hook-only `resume` branch of `ingestHookSignal`, and the backend resets the cycle on it directly (`sess.on('user-prompt', ...)`), so the reset never depends on winning that race.
- `NotificationManager.trigger` validates the transition before mutating the entry; a trigger on a DELIVERED/ESCALATED entry REPLACES it (timers cleared), so an unacknowledged entry can notify again.
- Focus suppression DEFERS, never drops: a notification parks in SUPPRESSED and is delivered when the suppressing condition clears (or discarded if acknowledged first).
- **Suppression is PER-CONNECTION, not global** (`server/core/client-presence.js`, pure; `backend.js` is the shell that registers one key per control-WS connection). An entry is suppressed only while there is at least one open connection AND EVERY one of them reports focused, i.e. every screen there is already shows the dashboard. A global "any client is focused" rule was correct with one device and wrong the moment remote mode allowed a paired phone: a dashboard left focused at the desk suppressed the phone forever. Zero connections never suppresses (nobody is watching), and a connection drops out of the count on close, so a dashboard that crashes while focused cannot suppress forever. A fresh connection counts as UNFOCUSED until it reports; the client reports on connect and on every focus/blur/visibilitychange. Because a focused tab can now RECEIVE a broadcast meant for another device, `public/notifications.js showDesktopNotification` declines client-side when `document.hasFocus()` - before the cross-tab claim, or the focused tab would win the claim and mute every other tab with it.
- Delivery needs an open dashboard tab: the primary channel broadcasts `notify` over the control WS and the browser raises the native Notification. With multiple tabs open, a short-TTL localStorage claim (`public/notify-dedupe-core.mjs`) lets exactly one tab raise it. No tab open = no browser notification (opt-in `config.osToast` is the OS-level fallback).
- **Telegram channel (opt-in, off by default).** `notifications/channels/telegram.js` pushes session notifications (complete / waiting / failed) to the operator's phone. Gated per delivery by `decideTelegramNotification`: `config.telegramNotifications === true` AND `config.telegram` botToken+chatId present (the SAME credentials the PR-review lane defines, so PR pings and session pings are independently switchable) AND ZERO open control connections. That last clause is the whole point: with a tab open anywhere the browser notification already reaches the operator on that device, so the rule is "ping the phone when nobody would see the browser notification", not "ping on every delivery". Deliberately not keyed on focus - an unfocused tab is exactly the case the browser notification is for. The channel is registered unconditionally at boot and reads live config per delivery, so the Settings toggle needs no restart and no re-registration; with the key absent the gate short-circuits and behavior is unchanged. The HTTP call is `server/telegram-transport.js sendTelegramMessage`, shared with (not copied from) `server/pr-telegram.js`, and never throws.

### Session Spawning (node-pty)

Sessions spawn `claude` via `pty.spawn()` from node-pty (NOT `child_process.spawn`).

- Claude CLI produces zero output with piped stdio - a real PTY is required.
- Must unset env vars before spawn: `CLAUDECODE`, `CLAUDE_CODE_SSE_PORT`, `CLAUDE_CODE_ENTRYPOINT`
- Do NOT use `shell: true` - pass args as array
- Terminal name: `xterm-256color`, default 80x24
- `dangerouslySkipPermissions` flag spawns Claude with `--dangerously-skip-permissions`
- **Resolve-then-branch spawn (Windows):** `claude` is resolved once at module load (`resolveClaudeCommand` -> `{ path, kind }`, `kind` from `classifyClaudeKind`). The pure `buildSpawnCommand` then picks the spawn form: a real PE image (`.exe`/`.com`) is spawned directly via `pty.spawn(<abs path>, args)`; `.cmd`/`.bat`/`.ps1` shim installs (or a failed resolution) fall back to `cmd.exe /c claude`. Spawning the `.exe` directly avoids cmd's double command-line parse and its console-title write. The `cmd.exe /c` path is now a shim-only fallback, not the default. Tests inject the resolved command via the `spawnCommand` constructor option.

### Auto-Resume and Shutdown (crash-safe by construction)

- **Live session-id capture.** Every MAIN-agent hook payload carries Claude's `session_id`, and that value names the resumable transcript, so `sessions.js ingestHookSignal` captures it from WHICHEVER hook arrives (`_captureClaudeSessionId`): it validates against `RESUME_ID_RE` (exported from `session/core/auto-resume.js`, same shape the manual Resume dialog enforces), sets the live `_resumeSessionId`, and emits `claude-session-id`. Do NOT key this off one event name: Claude Code does not reliably fire `SessionStart` (2.1.220 fires none at startup, live-probed both interactive and headless), and keying the capture there left the id, and therefore boot auto-resume, permanently dead in production. The tracking-only background-agent signals (`SubagentStart`/`SubagentStop`, `TaskCreated`/`TaskCompleted`/`TeammateIdle`, wakeups) return before the capture on purpose: they can describe a different Claude session than the one this card resumes. The emit fires only on an actual id CHANGE, because every hook now feeds it and the backend's listener writes config.json synchronously. The backend persists it to that project's `resumeSessionId` immediately (`persistSessionField` in `backend.js`, no-op for ephemeral sessions). Claude assigns a NEW id on every resume, so re-capturing keeps the chain current. Persisting at hook time (not shutdown time) is what makes a hard kill of Glissa lossless: there is deliberately no shutdown flush.
- **`wasActive` marker.** Per-project boolean persisted on flips only: true when a session enters STARTING/RUNNING, false on `user_kill` / DONE / FAILED. A crash mid-run leaves it true on disk, which is exactly the boot signal.
- **Boot auto-resume.** `session/core/auto-resume.js pickAutoResume(projects, config)` (pure) selects projects with `wasActive` + a `resumeSessionId`; `runAutoResume` in `backend.js` starts each matching DORMANT session through the spawn gate (ConPTY wedges under concurrent spawns) after the worktree reconciliation pass. Spawn appends `--resume <id>` (pre-existing plumbing at `sessions.js` spawn-args assembly). No captured id = stays dormant, never guess with `--continue`. Kill switch: top-level `autoResume: false` (default true; Settings dialog toggle). A stale id fails the session to FAILED, which flips `wasActive` false, so there is no retry loop.
- **Shutdown signals.** `server.js` routes SIGINT/SIGTERM/SIGBREAK/SIGHUP through one guarded handler that awaits the PTY kill reaps (`awaitReaps`, bounded 3000ms) before exit, matching the dashboard-triggered lifecycle path. Still no `uncaughtException` handler by design. Shutdown never writes config: `wasActive` staying true across a server shutdown IS the resume-next-boot case.

### Worktree Auto-Rebase (conflict avoidance)

A session worktree forks the integration branch at create time and, before this, first met it again at merge time, so two long-lived concurrent sessions accumulate a week of drift and pay for it as one large conflict. Two layers close that: a worktree that falls behind is rebased EAGERLY, and a conflict resolved once is replayed automatically everywhere.

- **The trigger is the change funnel that already exists.** Every worktree session runs its own integration-ref reflog watcher beside its own gitdir watcher (both started/stopped by `sessions.js _startWorktreeWatcher`, both nudging the same debounced `checkWorktreeChange()`), which is where the rebase decision now sits. A branch move therefore reaches each affected session directly, with no registry to fan it out. There is no timer: the reflog watch, the gitdir watcher and the turn-end recheck already fire at exactly the right moments. It is evaluated BEFORE that method's signature dedup, because the trigger it exists for leaves the signature byte-identical (`behind` is not part of the hash, so a moved develop under an untouched worktree would never get past the early return).
- **`session/core/rebase-gate.js decideAutoRebase` is pure and holds every guard**: disabled, teardown, merging, parked, busy, rebase-in-progress, dirty, current, conflict-cooldown. Allowed states are IDLE, COMPLETE, DONE, FAILED and DORMANT. WAITING is the load-bearing exclusion: `MERGEABLE_LIVE_STATES` accepts it because the operator is driving that merge, but "Needs Input" is a permission prompt PAUSING a turn, and the agent resumes into the very files an unattended rebase would have rewritten underneath it. The guard ORDER is stated only by `tests/rebase-gate.test.js`, so there is one place to change it.
- **`gitWorkspace.rebaseOnly` never stashes.** The merge paths stash uncommitted work around their rebase because an operator asked for that merge; this one runs unattended under a live agent, so a dirty tree is a hard refusal. It also merges nothing back: it replays the worktree's own commits onto the target and leaves the integration branch untouched. Serialized on the same engine queue as every other mutating method, and a no-op (`upToDate`) when the worktree is not behind, so an idle repo costs one `rev-list`.
- **A conflict is not escalated.** No park, no `mergeStatus` change, no notification: the worktree is left byte-identical to how it was found and the operator's eventual Merge click hits the same conflict, where the existing parked + resolve-prompt flow already handles it. What the failed attempt DOES record is a cooldown key, `${headSha}::${targetSha}`, so the same doomed rebase is not retried on every watcher nudge; it expires by itself the moment either sha moves, and a success clears it. Accepted limitation: a resolution recorded by a SIBLING session after the cooldown was armed does not re-trigger the eager rebase until one of those shas moves, because nothing about this worktree changed. It is not lost, only late, and the merge path replays it then. A rebase that never STARTED (`rebase-failed`: an index lock, a hook) arms nothing, since it is transient and the debounce already bounds the retries. Both real outcomes leave a `kind: 'rebase'` decision-trace entry, as does a rebase that completed while a turn started under it (`state-moved`); a routine skip leaves nothing, since it is what happens on almost every nudge.
- **rerere is shared by construction.** git's `rr-cache` lives in the COMMON gitdir, so enabling `rerere.enabled` once per repo shares every recorded resolution with every linked worktree for free. Glissa seeds that key only when it is UNSET, so an operator who wrote `rerere.enabled = false` means it and gets no replay. `rerere.autoUpdate` is never written to config at all, only forced PER INVOCATION on the rebases Glissa itself drives, so the operator's own merges keep git's default staging behavior.
- **The completeness proof is "no unmerged paths remain", and `git rerere remaining` may never be used as one.** rerere does not track BINARY content conflicts at all (any file with a NUL in its first 8k), so it prints nothing while a binary path is still unmerged; staging and continuing there commits git's target-side copy over the session's work, and when the staged tree then equals HEAD the step is silently `--skip`ped and the whole commit disappears (reproduced on both `rebaseOnly` and `mergeBack`; the regression is `tests/git-workspace-rebase.test.js`'s binary-conflict test). Forcing `rerere.autoUpdate` on for the rebase makes rerere STAGE exactly what it resolved, so a path still unmerged is by construction one rerere did not resolve, and that is what the loop checks. The loop is bounded (50 steps), forces `GIT_EDITOR=true` so no editor can hang it, and uses `rebase --skip` rather than `--continue` when a replayed resolution left the patch empty (which `--continue` refuses, stranding the rebase). Anything it cannot finish leaves the conflicted state untouched for the caller's capture-then-abort, so the pre-rerere behavior is reached byte for byte.
- **Which paths rerere replayed is deliberately not reported.** git drops a path from `MERGE_RR` as it resolves it, so by the time the rebase returns, `rerere status` and `rerere remaining` are both empty and no honest per-path list can be recovered (verified against git 2.44). The results carry a `rerereReplayed` boolean instead: naming the paths would mean guessing, and a guess in a forensic trace is worse than a silence.
- **Both rebase paths share it.** The merge-time `rebaseFfBranch` tries the replay before its existing capture-and-abort, so a merge whose conflict git has seen before now completes instead of parking, and sets `rerereReplayed` on the `mergeBack`/`mergeKeep` result.
- **A rebase suppresses the change funnel while it runs.** Mid-rebase a worktree reads clean and detached with ahead 0, which is exactly the shape `decideSignatureDemotion` self-heals a `pending-review`/`parked` gate to `none` on, with nothing left to re-arm it. `checkWorktreeChange` therefore returns early while `_autoRebasing` is set, the same way it does mid-merge, and the auto-rebase closes its own window with one `_scheduleWorktreeCheck()` on EVERY outcome, including a conflict and a thrown engine.
- **Kill switches:** `worktreeAutoRebase` and `worktreeRerere`, both default true, both control-WS settable with no Settings-dialog UI (precedent: `usage.rtkSavings`). Like every other construction-time option, `worktreeAutoRebase` reaches a session on its next construction; `worktreeRerere` is read once when the worktree engine is built, so it needs a restart. A `worktreeRerere: false` engine writes no rerere config and refuses to replay even a resolution that is sitting in the cache.
- **Non-goals.** It never rebases a dirty or busy worktree, never resolves a conflict itself beyond replaying one git already recorded, never merges anything into the integration branch, and never changes the merge-time parked flow.

### GitHub PR Auto-Review (opt-in, off by default)

An optional background lane that reviews the operator's OWN GitHub PRs and merges the clean ones, unattended. Inert unless BOTH `config.prReview.enabled` and `config.telegram` (botToken + chatId) are set; absent = byte-identical prior behavior. Configured from the dashboard Settings dialog's PR Review tab (`public/components/settings-dialog.html`, `public/dialogs.js`), persisted via the existing get-settings/update-settings control-WS flow. Unlike `osToast`, toggling takes effect immediately: `backend.js applySettingsReload` calls `pr-review-wiring.js restartIfConfigChanged()`, which restarts the poller only when a settings save or config.json hand-edit reload actually changes the `prReview`/`telegram` config key (`prReviewCfgKey`), so an unrelated save (cursorBlink, etc.) never disturbs a running poller. The restart itself is serialized through a `prPollerChain` promise chain: it awaits the old instance's `stop()` (which drains its in-flight reviews and pending state write, see `pr-poller.js`) before starting a fresh one gated by `prPollerShouldStart`, so a stale review can never race a new instance over the same result-file path, worktree, or state file. No server restart needed.

- **Poller.** `server/pr-poller.js createPrPoller(deps)` is IO-FREE (every side effect injected) and unit-tested with fakes. A `setInterval(intervalMinutes).unref()` (default 15m) drives one `tick()` per cycle behind a `tickRunning` re-entrancy guard. `stop()` is async: it clears the timer, then awaits a `running` Set of in-flight `runReview()` calls and the pending state-write chain, so a caller that reuses the same dependencies (a settings-triggered restart, or `shutdown()`) never races a stale review over the same result-file path, worktree, or state file. Wired at boot after `runAutoResume`; torn down in `shutdown()` (stop the poller, fire-and-forget since the process is exiting anyway, + reap the `reviewSessions` map).
- **Per project (`config.prReview.projects`, an explicit opt-in list of project ids).** `gh pr list` -> filter to the operator's own non-draft branches (skip forks/drafts/bots; pure `server/core/pr-review-core.js filterActionablePrs`) -> `planReviews` (head SHA changed since last review) and `planMerges` (phase `awaiting-checks`). State is one cross-project file (`~/.glissa/pr-review-state.json`, atomic tmp+rename), keyed `owner/repo#N` -> `{ reviewedHead, phase, inFlight, wasConflicting, pingedError }`; `inFlight` is reset on boot; entries are pruned when a PR leaves the open list (merged/closed elsewhere).
- **Review session.** One ephemeral headless `claude -p` per new head SHA, spawned through the shared `spawnGate` (START only, so reviews run concurrently under `maxConcurrentReviews`), keyed on the `exit` event, into a dedicated `reviewSessions` map (not surfaced as a card). A hard timeout (`spawnWithTimeout`, `reviewTimeoutSeconds` default 900) aborts a hung session (AbortController -> `sess.destroy()`) and frees the concurrency slot, so a stuck review cannot pin the cap forever. The verdict travels via a RESULT FILE the agent writes (`readReviewResult` in `backend.js`; missing/invalid/unknown -> ERROR, never a false clean), because `gh pr review` 422s on your OWN PR; findings go out as a `gh pr comment`.
- **Two lanes.** A clean PR is reviewed IN PLACE (diff-only: `gh pr diff` + reads at HEAD + `gh` remote ops, no checkout/worktree, no working-tree mutation), so it coexists with a live interactive session in the same repo. A CONFLICTING PR runs in an isolated `git-workspace` worktree (`gitWorkspace.create`, branch `glissa/pr-review/pr-N`), where the agent runs `gh pr checkout` + rebase onto `origin/<base>` + resolve + `git push`; a branch-in-use precheck (`gitWorkspace.listWorktreeBranches`) degrades to ERROR before spawning a doomed checkout, and every exit path `discard`s the worktree and deletes the leaked pr-head branch. `pr-poller` NEVER shells `git worktree` (it goes through `git-workspace`, the only module allowed to, per `tests/no-direct-git-worktree.test.js`); all `gh`/`git` go through `child-process-safe`.
- **Merge gate (poller only; the AGENT never merges).** `tryMerge` merges (`gh pr merge --rebase`) ONLY when: reviewedHead still equals the current head (a commit pushed after review is re-reviewed, never merged stale) AND `gh pr checks` is `green` (four-way `classifyChecks` in `pr-gh.js`: no checks -> `none`, never green; handles both CheckRun and legacy StatusContext shapes) AND the PR touches no `.github/workflows/` file (a gh error on that files query returns `null` -> fail CLOSED, defer to next tick). Own-non-fork-non-draft is already enforced by the actionable filter. Both no-checks and unknown-workflow fail closed, so a CI-less repo or a transient gh error never auto-merges.
- **Telegram.** `server/pr-telegram.js sendPrPing` (fire-and-forget, never throws) fires on ACTIONABLE transitions only (changes requested / conflicts resolved / merged / error); a clean-awaiting-checks PR is silent. PR-only: it is NOT a `NotificationManager` channel (no focus-suppression interaction, no session-complete pings). Session pings to the same chat are a SEPARATE opt-in channel (`config.telegramNotifications`, see Notifications) that shares only the `server/telegram-transport.js` HTTP call and the `config.telegram` credentials, so either lane can be switched on without the other.
- **Security.** The review session runs `--dangerously-skip-permissions` bounded by a best-effort `PR_REVIEW_DENY` deny-list (the real safety is that only the poller merges, behind the full gate above; the deny-list is a guard, not the guard). Consistent with the localhost single-user trust boundary below. Prereq when opted in: `gh` authenticated on the host.

### Radar / PostHog Auto-Fix Dispatch (opt-in, off by default)

The PostHog monitoring lane (`server/posthog-poller.js`, IO-free; `server/posthog-wiring.js`, its IO shell) normally answers a moved issue with a diagnose-only headless `claude -p` investigation. With `config.posthog.autoFix: true` a MAJOR issue instead gets an agent that reproduces the error and fixes it. Absent or false, every dispatch is byte-identical to before.

- **"Major" is the issue itself, not its blast radius.** `posthog-core.js isMajorIssue` is `spiking`, `regressed`, or `new`: an active issue nobody has seen before is worth fixing whether it hit two users or two hundred, so the predicate takes no user count and no `userEscalationThreshold`. The OBSERVATION ping (`new_issue`, once per issue via `pingedPhases`) follows the SAME rule, so detection and fix dispatch cannot disagree about what counts: a new active issue announces itself whatever its user count. Blast radius survives only as `planInvestigations`' `minUsersToInvestigate` floor, so a new issue too small to spend a session on is still named on the operator's phone, and one that does get auto-fixed pings `FIXED` at completion. `worsened` and `quiet` are never major. `decideJobMode` (pure) crosses the predicate with the opt-in and with whether there is a repository to commit in.
- **Reproduce first, and say so when you cannot.** The prompt (`buildFixPrompt`, same ids-only injection fence as `buildInvestigationPrompt`: an issue title is the monitored app's error message) orders a failing test or a minimal repro script BEFORE any patch, because a fix written from a stack trace alone is a guess. When reproduction is genuinely impossible the agent debugs from the code path, the PostHog evidence and the git history, still attempts the fix, and reports `reproduced: false` so the pull request body and the Telegram ping both admit it.
- **Isolated worktree, and the branch is the output.** The job runs in a `gitWorkspace.create` worktree on `glissa/radar-fix/<projectId>-<issueId>-<discriminator>` (ids scrubbed to a conservative charset), never in the live checkout, so it coexists with an interactive session in the same repo. The discriminator (a compact timestamp plus random hex, minted in the wiring since a core never reads a clock) is not decoration: a deterministic name collides with the REMOTE branch a previous fix for the same issue already pushed, and every later push then fails as non-fast-forward, burning the whole timeout on exactly the legitimate case (a regression after a fix). The worktree is discarded on EVERY exit path (success, error, timeout), inside the promise the poller tracks in `running`, so a shutdown or a settings restart drains the discard rather than leaking the checkout. `git-workspace.js` stays the only module that shells `git worktree`.
- **The agent commits; the SERVER pushes and opens the pull request.** `FIX_DENY` denies `Bash(git push:*)` and `Bash(gh:*)` outright, because a prefix deny-list cannot constrain a push TARGET (`git push origin HEAD:main`, a `+HEAD:main` refspec, a `:main` delete) or a `gh api --method PUT .../pulls/N/merge`: allowing either would have made "never merges" a matter of the agent's cooperation rather than a property of the lane. The agent's whole reach is a commit inside a throwaway worktree, and its result JSON is `{ verdict, reproduced, summary, prTitle, prBody }` with both texts normalized (control characters stripped, capped) before they can reach an argument. `posthog-wiring.js pushFixBranch` then does the rest through `child-process-safe` execFile argument arrays, never a shell string: it REFUSES the handoff when the branch diff touches `.github/workflows/` (downgraded to `NEEDS_HUMAN`, nothing pushed, so the "never touches CI" claim is structural instead of prompt-hoped), reports `ERROR` when a `FIXED` verdict committed nothing, then `git push origin <branch>` and `gh pr create --repo/--head/--base` with server-built values. The pull request url comes from gh's own stdout, never from the agent (`core.normalizePrUrl`, with the same https check repeated at the `radar-core.mjs` render boundary). Any failing step is `ERROR` naming the step and the honest branch state (pushed or not); the worktree is discarded either way.
- **Nothing in the lane merges.** Merging stays the PR-review lane's gated job (`config.prReview`) or the operator's. With BOTH switches on the handoff is agent-to-agent: a Radar fix PR can be picked up, reviewed and auto-merged by that lane behind its own gates (own non-fork PR, reviewed head unchanged, checks green, no workflow file), so an operator enabling `posthog.autoFix` alongside `prReview.enabled` should know unattended code can reach the base branch without a carbon unit in the loop.
- **No repo, no fix.** The lane's scratch directory holds no repository, and a `create` that reports `isGit: false` (not a checkout, no commits, branch already checked out elsewhere) or that fails outright is the same answer, so the job DOWNGRADES to a plain investigation. The result carries the mode that actually ran, and the entry, the ping and the inbox record all describe that one rather than the planned one.
- **One slot pool.** Fix jobs ride the same `maxConcurrentInvestigations` slots, the same `inFlight` bookkeeping and the same `stop()` drain as investigations; only the timeout differs (`fixTimeoutSeconds`, default 1800, validated 60..21600). A completed fix is not redispatched per tick: the existing re-investigation gates (a verdict on the entry, a genuinely new regression or spike) are what allow another one.
- **Verdicts and surfaces.** `FIXED` pings with the repro status and the PR link, `NEEDS_HUMAN` and `ERROR` reuse the existing verdict pings, `TRANSIENT` stays silent. The fix ping is the one verdict ping that is NOT deduped through `pingedPhases`: that list is carried forward forever, so deduping it meant a SECOND fix (the one a regression earns) opened a pull request in silence. The entry gains `fix: { at, verdict, reproduced, prUrl }` (no branch field: the server picks and pushes the branch, and the pull request states it) and the investigations-inbox record gains `mode` and `prUrl`, which the Radar panel renders as a "fix" chip plus a "fix PR" link.

### Usage Tracking (token counts and estimated cost)

The Usage lane reports Claude Code language-model tokens and estimated API list-price cost from local transcript files. It reimplements the ccusage v20 algorithm in Node and pins the behavior with usage core tests: transcript dirs from `CLAUDE_CONFIG_DIR`, `XDG_CONFIG_HOME/claude`, and `~/.claude`; recursive JSONL reads; global dedup by `message.id` + `requestId`, with sidechain collision handling; cache creation split into 5m and 1h buckets, with 1h charged at 2x input; 200k marginal tiering and explicit long-context threshold tiering; 5h UTC-floored blocks with gaps, burn rate, projection, and largest-completed-block token-limit warnings. It never parses PTY bytes, terminal output, or rendered screen content.

- **Lane attribution: what Glissa's OWN automation cost.** Glissa spawns its sessions, so it can answer the one usage question a transcript reader cannot: "the PR review lane cost $4.20 this week". `usage-lanes.json` beside the config file maps Claude session id to the lane that spawned it, written from the single place every id becomes known (the `claude-session-id` event a Session emits when a hook payload carries one) and joined onto usage entries by `entry.sessionId` in `server/core/usage-lane-core.js`. Retention matches `warehouseRetainDays`, applied on write as well as on read.
  - **Hooks DO fire for headless `-p` sessions, which is what makes the ephemeral lanes attributable.** Live-probed with the real `buildHookSettings` against a local listener: `UserPromptSubmit`, `Stop` and `SessionEnd` all arrive carrying the same `session_id` (`SessionStart` does not, consistent with the capture being keyed off whichever hook arrives rather than one event name). All three ephemeral lanes already pass `hookRouter` + `getHookPort`, so all three are attributable end to end: `pr-review`, `posthog`, `pack-distill`, plus `interactive` for managed cards.
  - **The lane ids are the names the lanes already call themselves** (`registerEphemeralSession`'s `logPrefix`), so there is no mapping table to drift. That seam is also where the recording happens: every ephemeral lane registers through it and it already knows both the lane and the session, so one listener covers all three rather than three copies.
  - **The join is exact, never inferred.** A session id is attributed only because Glissa recorded spawning it; everything else is `other` (a terminal session, a direct `claude` run, anything predating the ledger). Guessing from a cwd or project dir would silently mis-bill a lane, so it is not done. Vendor entries are never lane-attributed at all: Codex and Grok are dispatched outside the Session class, so Glissa never spawned them, and the section hint says so.
  - **Live window only.** The ledger is durable but the ENTRIES it joins against are not: the warehouse stores day-by-model rollups with no session id in them, so a history day cannot be split by lane, and `byLane` is null rather than fabricating attribution that was never observed.
  - **The UI hides itself until it has something to say.** The Glissa lanes section (between Totals and the current block) appears only once a lane other than `interactive`/`other` has spend, so a fresh install sees nothing rather than a row restating the totals above it.
- **Budgets: the operator's own ceiling, alerted once per period.** `usage.budget { dailyUsd, monthlyUsd }` (absent, the default, means off: no meters and no alerts, never a zero ceiling). The ladder lives in `server/core/usage-budget-core.js`: 50/75/100 percent, each firing at most once per day or per calendar month, reporting the HIGHEST newly crossed threshold and marking every lower one so a spend correction cannot walk back down and re-fire. Spend comes from `scanner.budgetSpend()` over the MERGED daily series (history included), so a meter and an alert can never disagree about what was spent, and the standing meters are computed server-side by the same core rather than reimplemented in the browser.
  - **Evaluated only on a COMPLETE pass**, exactly like the warehouse write, because firing a once-per-period alert off a partial pass's undercount would burn that threshold for the rest of the period.
  - **The fired state is durable**, in `usage-budget-state.json` beside the config file (`configSiblingPath`, tmp+rename, signature-guarded). Without it a restart would re-alert 50/75/100 every time, which is how an alert channel teaches its operator to ignore it. A corrupt or missing file starts empty and warns: that can only ever RE-fire an alert, never suppress a real one, so it fails toward noise rather than silence. An unwritable path costs the mark, not the alert or the pass.
  - **Delivery is dashboard-first.** `{ type: 'usage-budget-alert', scope, threshold, spentUsd, budgetUsd, periodKey, text, ts }` is broadcast unconditionally and is deliberately NOT in the control replay retention list (`REPLAYABLE_EXACT`): an alert is a moment, and replaying it on reconnect would re-alert a crossing that already happened. The browser raises it through the existing notification path with the cross-tab claim keyed on scope plus period plus threshold. It passes `ignoreFocus`, the one place that differs from a session notification: the server applies no focus suppression to budget alerts, and a focused dashboard says nothing about whether the operator is on the Usage tab, so declining would drop the alert rather than avoid a duplicate. Telegram reuses `decideTelegramNotification` unchanged, so the zero-connections rule cannot drift from the session channel's, and the alert text ships ON the message so both channels send the same string by construction.
  - **The dot at 90 percent.** A budget at or past `BUDGET_ATTENTION_PCT` contributes its own part to `usageAttentionSignature`, joining the plan-limit and anomaly arbiters rather than replacing either: a budget is the operator's own ceiling, and the other two measure something else.
- **Savings: what the token-saving systems are worth, beside what was spent.** Two independent halves on one `savings` field of the report, deliberately never blended into a single number, because one counts work Glissa never did and the other prices tokens against a list price nobody was billed. The rules are pure, in `server/core/usage-savings-core.js`. **rtk** keeps its own durable stats, so Glissa only reads them: `server/usage-wiring.js` execs `rtk gain --daily --format json` on the resolved binary (both the exec and the path lookup are injected deps) and normalizes the payload. The figures are MACHINE-WIDE, covering every rtk-hooked call on this host rather than only Glissa's sessions, and the UI hint says so. Every failure mode (opted out, no binary on the machine, exec error, timeout, unparseable JSON, an unrecognized shape) lands on the same `{ available: false }`: there is no partial version of a number rtk vouches for, so the tile is absent rather than showing a zero it cannot stand behind. A successful reading is TTL-cached for 60s because a report is pulled on every turn end while the tab is open; a FAILED reading is deliberately not cached, so an rtk installed or repaired mid-session appears on the next pull instead of after a restart. Kill switch: `usage.rtkSavings` (default true, control-WS settable, no Settings-dialog UI), and switching it off skips the path probe entirely. It is deliberately NOT gated on `config.rtk`, which governs only whether Glissa injects rtk's hook into the sessions it spawns; the stats are worth reading either way. **Prompt cache** savings are Glissa's own arithmetic over the report's Claude model rows: per row, `cacheRead * (input rate - cache read rate)` clamped at zero, using the same `ratesForPrice` the cost estimate charges with (exported from `server/core/usage-pricing-core.js` rather than reimplemented, so the two cannot drift). A FLAT-rate estimate, ignoring the above-200k tier on purpose: the model rows carry no per-request context size to tier by. Other vendors are skipped (an absent vendor is Claude, matching the aggregate's own rule), a model with no price contributes its TOKENS but no dollars and is named so the figure reads as a floor, and no Claude cache reads at all yields null rather than a zero saving. The whole `savings` field is always present on a successful report, worst case `{ rtk: { available: false }, cache: null }`, and it is built defensively so an optional figure can never cost the report itself.
- **History and insight: the warehouse outlives the transcripts.** Claude Code deletes transcripts after about 30 days, so a lane that only reads them reports a series that silently truncates and every longer view is quietly wrong. `server/usage-scanner.js` therefore persists per-day-per-model rollups to `usage-warehouse.json` beside the resolved config file (so a temp `GLISSA_CONFIG` never writes into the operator's real `~/.glissa`, the same rule uploads and recordings follow), using the pure merge rules in `server/core/usage-warehouse-core.js`. Retention is `usage.warehouseRetainDays` (default 365, validated 30..3650), deliberately independent of transcript retention.
  - **Only a COMPLETE pass writes.** A partial pass has seen an arbitrary slice of the tree, so merging its day totals would persist an undercount as durable truth. That is also why continuation storms need no debounce timer: they are all partial and write nothing. A completed pass whose records are byte-identical to the stored ones also skips the write, so an idle machine rescanning on its interval rewrites nothing. Writes are tmp+rename; a corrupt file starts empty with a warning and the next complete pass rebuilds what it can still see; an unwritable path degrades to a warning, never a failed scan.
  - **Live wins inside live coverage, history fills in behind it.** `mergeWarehouse` is given `liveDays` (the days the scan actually produced) so a day the live read covers always REPLACES its stored copy rather than adding to it. On the read side only days STRICTLY OLDER than the earliest live day come from history, so a day the live scan is still filling in is never topped up from a stale copy. Those rows are marked `source: 'history'` and labelled in the UI, because a day Glissa remembers is a different claim from one it can still see.
  - **The warehouse extends the DAILY series only.** Totals, per-model rows, per-session rows, blocks, burn rate and plan limits stay live-only, because the stored rollups are day-by-model and nothing finer. What is derived from the daily series does inherit history: the week and month views, the heatmap, and the anomaly baseline.
  - **Week, month and heatmap are computed CLIENT-side** in `public/usage-view-core.mjs` from the merged daily rows the report already ships, so the wire gained only the history rows and the anomaly field, and a period total can never disagree with the days under it (pinned by a conservation test). Weeks start Monday and are keyed by that Monday, so a week spanning a month boundary stays one bucket. A period is `history` only when EVERY day in it is. The heatmap is a 16 week CSS grid whose tone is a fixed fraction of the WINDOW's own peak rather than a quantile (quantiles guarantee dark cells even on a quiet fortnight, which reads as heavy usage that is not there), and an observed zero is drawn differently from an unobserved day.
  - **Anomaly is machine-level and evaluated server-side** (the burn check needs block internals), shipped as `anomaly: { daily, burn }`. The baseline is the trailing 30 days EXCLUDING today, sliced before it reaches `dailyBaseline`: a sparse multi-month mean makes an ordinary day look like a spike. The wording always names the comparison ("Today is 3.1x the 30 day average"), a flagged anomaly raises the tab dot on its own since no threshold was crossed to surface it, and the quiet case still prints one muted line because an alarm that only ever appears cannot be trusted to be working. No notification and no per-card chip: per-session baselines are a different data model (sessions are short and unevenly sampled) and are deliberately out of scope.
- **Multi-vendor: Codex CLI and Grok CLI ride the same pipeline.** Their line parsers are pure and separately parity-validated (`server/core/usage-codex-core.js`, `server/core/usage-grok-core.js`), and the scanner walks their trees beside the Claude ones with the same incremental machinery. Roots: Codex from `CODEX_HOME` (comma-split like `CLAUDE_CONFIG_DIR`) else `~/.codex`, using `sessions/` plus `archived_sessions/` and treating the home as a flat JSONL dir ONLY when neither exists (a real `~/.codex` also holds `history.jsonl` and plugin fixtures, which are not usage); Grok from `GROK_HOME` else `~/.grok`, reading only `sessions/**/updates.jsonl`. A missing vendor home is silently absent, never an error, unlike `CLAUDE_CONFIG_DIR` which is an explicit claim that a directory exists. Kill switches: `usage.vendors.codex` / `usage.vendors.grok`, both default true, both surfaced in the Settings Usage tab; a false skips that vendor's walk entirely so its tree is never stat'ed.
  - **Per-file state carries more than an offset now.** Codex `token_count` lines report CUMULATIVE totals and name their model in an earlier `turn_context` line, so the per-file state object holds a `vendorState` (running total snapshot plus current model) beside `{ size, mtimeMs, offset, carry }`. An appended read continues from that snapshot; without it the new cumulative total would be treated as one fresh delta and re-count the whole session. The parsers MUTATE that state, so the read-failure rollback snapshot clones it.
  - **Dedup is per vendor and namespaced.** Each vendor core owns its identity rule (Codex has no message id, so it is session plus timestamp plus counters; Grok uses `prompt_id`) and puts its vendor name in the first segment of the key, so one entry store is safe and a Claude key can never collide with a Codex or Grok one. Pinned by `tests/usage-scanner-vendors.test.js`. The same Codex rollout appearing under both `sessions/` and `archived_sessions/` resolves in favour of the active copy, matching ccusage.
  - **Pricing.** `server/data/claude-pricing.json` now covers anthropic plus the openai gpt-5 family (see its `_meta.coverage`), because Codex entries arrive with `costUSD: null` and need a table. The optional LiteLLM fetch trim was anthropic-only, which silently dropped every gpt entry and left Codex priced from the snapshot alone; it now keeps both providers (`FETCH_PROVIDERS`) and still drops everything else rather than taking the whole upstream file. Codex pricing is FLAT with respect to service tier: ccusage prices it flat and the parity harness matched without tier differentiation, so the parser deliberately ignores the service tier. Grok is absent from the table on purpose: it records its own cost per turn (billing ticks, or the parser's published rate card), so its rows keep the transcript's figure and never route through the price table or the missing-pricing warning.
  - **Claude-only surfaces, stated in the UI.** 5h blocks, burn rate, projection, the token-limit reference and the official plan limits are Claude subscription concepts, and the per-card chips are attributed by CLAUDE session id, so all of them count Claude entries only. Where that could read as an inconsistency next to a multi-vendor total, the section hint says "Claude only" (`claudeOnlyHint`, shown only once a non-Claude vendor actually has data).
  - **Everything vendor-aware is additive.** Report rows gain `vendor` (model and session rows) or `vendors` (a daily row legitimately spans vendors, so it carries the set rather than a scalar that would have to pick one), and `totals.byVendor` lists only vendors that contributed. An all-Claude machine reports exactly one vendor key and renders identically to before, which is also how the dashboard tells "no other vendor" from "another vendor at zero".
- **Lane lifecycle.** `config.usage` is ON by default through `resolveUsageConfig`; `enabled: false` is fully inert and constructs no scanner. The lane starts lazily on the first control connection because the first machine-wide scan is the expensive pass. After that, `server/usage-scanner.js` tracks `{ size, mtimeMs, offset, carry }` per file and reads only appended bytes unless a file shrank or a forced report asks for a rebuild. A byte-budgeted pass that returns `partial: true` is continued on a 15s timer only while a dashboard is connected; normal interval scans default to 5 minutes and also do nothing with zero control clients. Post-turn refresh is debounced 2s because Claude Code flushes transcript entries after the Stop hook.
- **Attribution and protocol.** Per-card usage comes from entries whose in-line transcript `sessionId` matches the card's live `resumeSessionId`; filename identity is only a fallback for report rows, never the card chip. The small pushed message is `usage-sessions` and is replayed on connect. The full report is pulled by `request-usage-report` and returned as `usage-report`, with a cached replay for a reconnect after a report has been built.
- **Pricing.** `server/data/claude-pricing.json` is a committed LiteLLM snapshot trimmed to Claude fields. If `usage.fetchPricing` is true, `server/usage-pricing.js` optionally fetches the public LiteLLM pricing table, stores a 24h cache under `~/.glissa/litellm-pricing.json`, and overlays fetched models onto the snapshot. Fetch failures are silent fallback, not a lane failure. Unknown models cost 0 and are surfaced as `pricing.missing`.
- **Plan limits are OFFICIAL, and arrive through a managed statusLine.** Claude Code publishes the real `/usage` rate limits (`rate_limits.five_hour` / `seven_day`, each `{ used_percentage, resets_at }`) in its statusLine payload, and nowhere else a process outside it can read. Glissa therefore injects a `statusLine` into the per-session managed `--settings` file pointing at `session/statusline-relay.js`, which POSTs the raw blob to `POST /hook/:glissaId/statusline?t=<token>` on 127.0.0.1. Kill switch: `usage.planLimits` (default true), and `usage.enabled: false` disables it too, so an opted-out session's settings file is byte-identical to the pre-statusline one. Like every other spawn-time setting (`rtk`, `detectScheduledWakeups`), toggling it applies to the NEXT spawn: a live session keeps the statusLine it was started with, though the ingest and the snapshot read are both gated live, so switching it off stops the data immediately either way.
  - **The relay MUST chain the operator's own statusLine.** A statusLine in a per-session settings file REPLACES the global `~/.claude/settings.json` one rather than adding to it (live-verified, 2.1.235), so without chaining, enabling this feature silently deletes the operator's HUD. The injector reads their command at spawn time (best effort; absent is fine), base64s it into the relay's argv to survive two levels of quoting, and the relay spawns it with the consumed stdin replayed and stdout inherited, exiting with its code. The POST and the chain run in PARALLEL and the POST is abandoned after 1500ms: this process sits in front of the operator's status line, so nothing here may add latency to it. With nothing to chain the relay prints a compact model-and-cost line. Windows note: the statusLine command runs under git-bash (a backslash path dies silently with 127, hence the forward-slashing and single-quoting), while the relay spawns the chained command through `shell: true`, which is cmd.exe there; a chained command relying on bash-specific syntax should be a plain executable invocation.
  - **Cadence, and why the throttle is not optional.** The callback fires once at startup and then per assistant/tool step with a ~300ms floor, and NOT AT ALL while idle (a change signal, not a heartbeat; never fired in headless `-p` sessions). `prompt_id`, `session_name` and `rate_limits` are absent on the startup invocation and appear from the first post-API-response one, and each window can be independently absent. So `server/core/usage-statusline-core.js` rounds the percentages (they carry binary-float noise) and `shouldBroadcastPlanLimits` puts a message on the wire only when a rounded percentage or a reset time actually moved. Ingest is O(1) with no fs: it runs inside every live turn of every session, on the one event loop they all share.
  - **The snapshot is machine-wide, the cost is per session.** Rate limits belong to the ACCOUNT, so `server/usage-wiring.js` keeps one freshest snapshot (latest ts wins) and replays it to every client on connect, broadcast as `{ type: 'plan-limits', ts, fiveHour, sevenDay, source: 'statusline' }`. The payload's own `cost.total_cost_usd` is stamped per conversation as `officialCostUSD` on the `usage-sessions` rows, keyed by Claude session id in a capped map (a new id per resume would otherwise grow forever). It sits BESIDE the scanner's estimate rather than replacing it, and the card chip labels which one it is showing.
  - **Provenance is never implied.** When official five-hour data exists it outranks the largest-completed-block heuristic for the attention dot and the block tone (`blockAttentionTone` in `public/usage-view-core.mjs` takes the plan limits as its second argument); without it the heuristic still governs, labelled "estimated from the largest completed block". A stale snapshot is shown with its age ("showing last-known usage (Xm old)") past 60 minutes rather than hidden or silently swapped for the estimate.
  - **Security.** The statusline reply stays the plain `{ ok, reason }` JSON: the `additionalContext` injection shape is UserPromptSubmit-only, and a telemetry channel must never become a second injection point. `mapHookToSignal` returns null for the event, so it validates the token exactly like every other hook and emits NO detection signal. The raw payload is neither stored nor recorded (it carries `transcript_path`, `cwd` and `prompt_id`, none of which is worth keeping to draw two progress bars), and the relay refuses any target that is not loopback http.
- **Wire units, and the two traps in them.** `tokenLimit.pct` is a RATIO of the largest completed block (`server/core/usage-blocks-core.js`, pinned by `tests/usage-blocks-core.test.js`), NOT a percentage, and `scan.dirs` is an ARRAY of resolved directories, not a count. Reading either at face value in the dashboard is silent: treating the ratio as a percent left the token-limit meter near empty, the line reading `0%`, and the tab attention dot unable to fire at all, while a finite-number check on `dirs` dropped the directory clause from every real report. Both are normalized once, at the frontend boundary, by `limitPct` and `scanLine` in `public/usage-view-core.mjs`.
- **Attention is predictive, not only reactive.** `blockAttentionTone` in `public/usage-view-core.mjs` takes the WORSE of where the block already is (`limitPct`) and where its burn rate lands it (`projectedLimitPct`), against the same 80/100 thresholds, and that one verdict drives the tab dot, the block tiles and the projection line. Keying the alarm on the current percentage alone fires it only after the tokens are spent, which is the wrong end of a burn-rate warning.
- **Today is the SERVER's day.** Daily buckets are keyed on the server clock, so `reportDayKey` resolves the today tile from `report.ts` in `report.tz` via `Intl`. Asking the browser what day it is reads the wrong bucket for any viewer in another zone, which remote mode makes routine, and the tile then silently shows `$0.00` for a day that cost money.
- **Limitations.** Costs are estimates, not bills; a Claude subscription does not bill per token. The scope is local transcripts on this machine, plus configured extra project dirs. Non-Claude work, remote transcripts, provider-side billing adjustments, and any model missing pricing data are outside the number.

### Session Recording (forensics)

Every real session writes a JSONL recording to `~/.glissa/recordings` (never a cwd-relative directory: recording is on by default and must not scatter through whichever repo the server was launched from). Two verbosity levels, ONE v2 format, declared in the header's `records` field so a reader can tell them apart without scanning:

- **`signals` (default, kill switch `recordSignals: false`).** Header, every hook callback with its payload VERBATIM (`background_tasks`, `session_id`, teammate fields: the exact evidence a detection post-mortem needs), every state transition with its detail, every `decision` record (the per-session decision trace from `session/core/decision-log.js`: each signal's mapper/gate outcome, each `decideGateRelease` verdict, and each notification decision with its reason), footer. The ONE hook callback exempted is pack read telemetry (`PostToolUse`/`Read`), which fires once per tool call and would bury everything else; its whole-session aggregate rides the footer's `packReads` instead. Tiny. The detection design is only debuggable after the fact if this is on, so it is on: a completion-gate incident with recording off costs a forensic reconstruction from Claude transcripts instead of one grep.
- **`full` (opt-in, `capture: { enabled: true }`).** The above plus raw PTY bytes, user input and resizes. Bulky, and only replay-harness work (`detection/replay.js`, whose fixtures are v2 recordings) needs it.

Bounds, because this runs unattended: the file opens LAZILY on the first record (a DORMANT session that never starts leaves nothing behind), rotates at `maxFileSizeMB`, and each `open()` kicks off a fire-and-forget async sweep that keeps the newest `retainFiles` (default 20) recordings PER SESSION and drops anything past `retainDays` (default 7). The sweep is fully async by design (all sessions share one event loop) and best-effort: a locked file is skipped, never retried. Nothing awaits it except tests (`recorder.retentionDone`).

### Context Packs (the context mill: assembly + spawn delivery + live notices)

A pack gathers local context (docs, house rules, curated skills) into a versioned, token-budgeted directory that a session is pointed at with `--add-dir`. Assembly, spawn-time delivery, auto-rebuild, the live per-turn notice channel, and read telemetry so far. A project with no `packs` key spawns byte-identically to before. Plan and milestones in `docs/plan-context-mill.md`.

- **Specs and sources are version-controlled inside the install** (`packs/specs/<name>.pack.json`, `packs/sources/**`), built output is runtime state under `~/.glissa/packs/built/<name>/`. Relative source patterns resolve against `packs/`, so a spec reads the same from a checkout or a global install.
- **`server/core/pack-core.js` is pure and holds every decision**: spec validation (unknown keys are an error, not a silent no-op), the `**`/`*`/`?` glob matcher the walker drives, the `chars/4` token estimate (named `tokenEstimateMethod` in the manifest so nobody mistakes it for a tokenizer), and `planPackBuild` returning the output file map plus `manifest.json`. It never reads a clock: `builtAt` is passed in, like the other cores take time.
- **Deterministic by contract.** Same spec plus same content yields byte-identical output, which is what makes the version a hash and a rebuild diffable. The version hashes every DELIVERED file (sources, rules, description, skills), not just the source files, so an edited rule cannot ride out under an unchanged version; `manifest.json` is excluded because it carries `builtAt`. Nothing else in the output is stamped with a build time, deliberately.
- **Budgets are hard gates, and a failed build writes nothing.** `budgetTokens` bounds the whole pack, and the always-loaded `CLAUDE.md` index has its own tighter cap (`MAX_INDEX_TOKENS`), because the discovery tier is the one context rot bites first. A source pattern that matched no file is also a build error rather than a silent hole.
- **`server/pack-builder.js` is the thin IO shell**: async walk (skipping `.git`, `node_modules`, and any symlink, since a junction can point back up the tree), then publish into a tmp sibling dir, rotate `current/` to `previous/`, and rename the tmp in. A failed build leaves the last good `current/` untouched.
- **Output layout targets `--add-dir`**: a thin `CLAUDE.md` index, one `.claude/rules/NN-<slug>.md` per source group, copied `.claude/skills/**`, and `manifest.json` carrying per-source hashes, version, `builtAt`, and the budget verdict.
- **`glissa pack build [name]` / `glissa pack list`** (`server/pack-cli.js`, in `server/` for the same files-whitelist reason as `pair-cli.js`) are the manual trigger; `server/pack-service.js` is the automatic one.
- **A build that would republish the same version writes nothing** and reports `unchanged: true`. This is what makes the rebuild loops cheap enough to run unattended, and it is also correctness: Claude Code hot-reloads skills out of a delivered pack dir, so rewriting identical bytes would poke every live session for no reason.
- **Auto-rebuild is two loops, and the cheap one is the guarantee** (`server/pack-service.js`, IO-free with injected deps like `pr-poller.js`). Per spec, one recursive debounced `fs.watch` per source root (`pack-builder.packWatchRoots`: each pattern's glob-free root plus each skill dir, a file's parent rather than the file, existing dirs only) rebuilds just that pack; a `.unref()`ed 15 minute sweep, re-entrancy guarded, rebuilds every spec and covers what `fs.watch` drops, a root that did not exist at boot, a spec-file edit, and platforms without recursive watching. Every rebuild runs through one promise chain, so two triggers can never publish the same pack dir at once. Recursion is why this does not use `detection/watch-debounce.js` directly: that module watches one directory non-recursively, exactly right for the gitdir watchers it was written for, so `server/pack-watch.js` reuses its debounce and stop lifecycle and supplies its own `fs.watch` handle. No specs means no watchers and no timer. Kill switch: top-level `packsAutoRebuild: false`, read once at boot (config file only, no Settings UI, restart to change).
- **A published rebuild broadcasts `{ type: 'pack-updated', name, version }`** on the control WS, and the connect snapshot carries a `packVersions` map of the latest built version per pack. A card whose delivered version (`snapshot.sessions[].packs`, plus a `session-packs` broadcast when a spawn resolves its packs) differs from the latest shows a "pack stale" chip (`public/session-card/pack-stale-core.mjs` holds the rule; a pack with no known latest version is never judged). `pack-updated` is deliberately NOT retained in the control replay log: the snapshot a reconnecting client already receives repairs the whole map, which is the retention rule that log applies.
- **A rebuild does not touch a live session, and reaches it only halfway.** Skills under an added dir hot-reload mid-session (verified CC behavior), so a rebuilt skill lands in a running session for free; a changed `CLAUDE.md` or `.claude/rules` file does NOT, and reaches only the next spawn. That asymmetry is why the chip exists, and what the notice channel below closes.
- **The live notice channel is one line on the next `UserPromptSubmit` hook response.** When `pack-updated` names a pack a live session actually SPAWNED against, `backend.js` calls `sess.notePackUpdate(name, version)` (a session without that pack in its delivered list is never armed, and no boot seeding exists or is needed: a spawn resolves the built version it delivers, so delivered equals latest until a rebuild publishes). The next accepted `UserPromptSubmit` callback for that session gets `hookSpecificOutput: { hookEventName: 'UserPromptSubmit', additionalContext: <notice> }` added to its reply. That exact nesting with the matching event name is the ONLY shape Claude Code injects (a top-level `additionalContext` is silently dropped, live-verified 2.1.235), and `UserPromptSubmit` is the only reliably per-turn injection event, so no other event's response ever carries it. **With nothing pending, the response body is byte-identical to `{"ok":..,"reason":..}`** (pinned in `tests/backend-pack-notice-hook.test.js`). The block is built in the ROUTE, not in `hook-source.js`: the router is a signal mapper with no Session reference, while the route already resolves `glissaId` and only an accepted (200) callback may consume a notice, so a bad token cannot drain one. The notice text is **Glissa-authored only** (`session/core/pack-notice.js`, pure): pack name, delivered version, new version, and fixed guidance to re-read the added directory if relevant. Never a byte of pack content, so the live channel cannot become an injection relay, and hard-capped at a few hundred chars (the CC limit is ~10000) with the pack list truncating to an "and N more" tail. It is consumed on read, so one staleness change costs one notice no matter how many turns follow, and it re-arms only when a NEWER version arrives. A spawn, a PTY exit and `destroy()` clear it, since the next spawn re-resolves what is delivered and re-reads the pack files anyway. Taking one leaves a `kind: 'pack', decision: 'notice'` entry in the decision trace, so a recording shows exactly which turn got injected context.
- **The distiller is opt-in source generation, not assembly.** `config.packDistiller` gates the scheduled lane only; `server/pack-distiller.js` runs headless `claude -p` sessions that regenerate derived files under `packs/` when their stamped source hashes drift. Each derived file starts with a `glissa-distill v1` stamp from `server/core/distill-core.js`; each lane run accepts only a result-file verdict of `DISTILLED`, `NO_CHANGE`, or `ERROR`, then rechecks the written file's stamp before reporting success. The M3 watcher sees the distilled file write and rebuilds the pack automatically, so the distiller and deterministic builder compose without direct coupling. Manual `glissa pack distill [name] [--dry-run]` is always allowed; dry run reads and hashes only, and spawns nothing.
- **Sources are local files only.** Pack bytes land in `--dangerously-skip-permissions` sessions, so v1 keeps the trust boundary at "files the operator already controls"; remote sources stay out until they can go behind a scan gate.
- **Spawn delivery is per project, hand-edited.** A project record may carry `packs: ["company-context"]` (deliberately NOT a control-WS settable key, like `remote`; config.json is the whole M2 interface, and an edited list recreates the session on reload the way a `dangerouslySkipPermissions` change already does). `sessions.js._resolvePacks` asks `pack-builder.resolveBuiltPack` for each name's `<builtRoot>/<name>/current`, appends one `--add-dir <dir>` per resolved pack next to the `--settings` block (so the initial-prompt positional stays argv-last), and stamps the delivered `{ name, version }` onto `toSnapshot().packs`. `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` is added by `spawn-env.js` ONLY when at least one dir was added, because without it Claude Code loads an added dir's skills and commands but not its `CLAUDE.md` or `.claude/rules` (live-verified, 2.1.235). A pack that is not built, or whose `manifest.json` is unreadable, is SKIPPED with a `kind: 'pack'` entry in the decision trace: additive context must never block a spawn or guess at a directory. The list is normalized defensively (`pack-core.normalizePackNames`: non-array, non-name, duplicate, and over-cap entries are dropped with a warning), since a hand-edited config must cost the bad entry and nothing else. Pack dirs live under `~/.glissa`, outside every repo, so worktree sessions need no special casing; the ephemeral PR-review and PostHog lanes consume `config.prReview.packs` and `config.posthog.packs` through the same normalization. Known limitation, not solved here: an interactive spawn in an untrusted cwd blocks on the workspace-trust dialog before any pack loads.
- **Measuring pack usefulness starts with consumption: did the agent ever open what it was handed.** A session that DELIVERS at least one pack gets a SECOND matcher-scoped `PostToolUse` entry (`matcher: 'Read'`, beside the existing `ScheduleWakeup|CronCreate|CronDelete` one) in its injected settings file; a session with no delivered pack, or with `config.packReadTelemetry: false`, writes a settings file byte-identical to the pre-telemetry one (pinned in `tests/session-pack-reads.test.js`), so the matcher is the whole cost and only pack-carrying sessions pay it. `hook-source.js` maps that callback to a `pack-read` signal that is TRACKING-ONLY like `SubagentStart`: it never reaches the StatusSource, carries no confidence, and cannot move a state. `sessions.js._trackPackRead` classifies `tool_input.file_path` against the delivered packs' dirs with the pure `session/core/pack-read-tracker.js` (normalization keyed on path SHAPE, not `process.platform`, so a drive letter or UNC prefix folds case and both slash kinds compare equal wherever the code runs); a path outside every pack dir is dropped silently, which is most of them. Counts ride `toSnapshot().packs[].reads`, so they update on whatever already carries a snapshot and cost no per-read broadcast; the per-card debug overlay lists them, and the pack-stale chip's tooltip adds them beside the staleness line. `readsSinceNotice` appears only once an M4 staleness notice has actually been taken (`takePackNoticeContext` arms the counter), which is how the live channel's effect becomes visible: a notice that produced zero re-reads did nothing. **The per-read hook callbacks are deliberately NOT recorded at the `signals` level** (one record per Read would bury the transitions and decisions a recording exists for); the quiet rule sits at the recorder ingest seam in `ingestHookSignal`, and the whole-session aggregate is written into the recording FOOTER as `packReads` instead. A `full` capture still keeps every callback, since raw fidelity is its entire point. Consumption is only half the question: pair it with the usage lane (`server/usage-wiring.js`) for the cost side of a pack-on vs pack-off comparison.

### Security: Trust Boundary

Glissa binds to `localhost` only. Both WebSocket channels (data and control) have **no authentication** - any process on the local machine can connect. This is acceptable for a single-user dev tool but means:

- Do NOT expose Glissa's port to the network (no `0.0.0.0` binding)
- The `dangerouslySkipPermissions` option is settable via the control WebSocket; any local process can create a permissionless session
- There are TWO HTTP write ingresses. The first is `POST /hook/:glissaId/:event` (Claude Code hook callbacks): localhost-only and gated by a per-session bearer token (unguessable, written into that session's managed settings file), so the trust level is "can read this session's settings file" = same as reading the PTY. Keep that token check if you touch the route. Its RESPONSE is also an ingress now (a `UserPromptSubmit` reply can inject `additionalContext` into the turn), so only an accepted callback may consume a pack notice and the injected text is Glissa-authored only, never pack or caller content. See "Context Packs".
- The second is `POST /upload/:sessionId` (the phone key strip's Image button): raw image bytes in, saved under `<config dir>/uploads/<sessionId>/`, and the saved absolute path bracket-pasted into that session's PTY (no CR, so the operator sends it). It is mounted AFTER the remote-auth middleware, so a remote caller must carry a valid pairing cookie; on the local listener it carries the same trust as the control WS, which can already spawn a session anywhere. Guards: unknown session 404, content-type whitelist (`image/png|jpeg|webp|gif`) 415, a streamed 15MB cap 413 with the partial file removed, and 409 (file deleted) when the session has no live PTY to paste into. Uploads are retained newest-20 per session. Pure rules in `server/core/upload-core.js`, HTTP coverage in `tests/backend-upload-route.test.js`.
- If network exposure is ever needed, add authentication to the control WebSocket first

#### Remote Mode (opt-in, off by default)

Remote access is a SECOND listener, not a wider bind. `config.remote` (`{ enabled, port, publicHost, allowedOrigins }`) is absent/false by default and every branch is then inert: `tests/backend-remote-disabled.test.js` boots the backend on a default config and pins that no `/pair` route is mounted, no middleware runs, no pairing file is created, the hook route answers exactly as before, and an upgrade refusal still writes nothing on the wire.

- **Two listeners, one Express app.** The local listener stays `127.0.0.1:<port>` and unauthenticated. When enabled, `server.js` opens a second HTTP server on `remote.port`, also bound loopback (it is the upstream a reverse proxy such as `tailscale serve` fronts), and `backend.remote.attach()` gives it the SAME app and upgrade handler, so a route cannot exist on one listener and be missing from the other. `remote.publicHost` only builds pairing URLs; it binds nothing. `remote.port` must be set and must differ from `port`, or boot is refused (`tests/remote-config.test.js`).
- **Trust is the listener port, never a header.** `session`-facing decisions come from `server/core/request-trust.js`: `classifyRequestOrigin({ localPort, remoteListenerPort })`. A reverse proxy makes remote traffic look loopback at the IP level, so an IP or `X-Forwarded-For` rule would hand every visitor local trust. On the remote listener only `/pair/*` is reachable without a cookie; `/hook/` is deliberately NOT exempt (strictly tighter than today, so the hook route itself needed no change). An upgrade for a path Glissa does not own is left untouched on the local listener (Vite HMR must still claim it) but destroyed on the remote one, where nothing else is listening and returning would strand an unauthenticated socket open. Full matrix in `tests/request-trust.test.js`.
- **A pairing cookie is RCE as the server account.** The control WS accepts an arbitrary project path plus `dangerouslySkipPermissions`, so a paired device can run code as this user. Pairing URLs are therefore single-use passwords with a 10 minute TTL, never logged, never echoed into an error page, and never persisted in plaintext (`tests/pairing-token.test.js`, `tests/pairings-store.test.js` asserts the token and cookie value never appear in the file).
- **Pairing state.** `~/.glissa/pairings.json` (beside config.json, mode 0600) holds hashes only. `glissa pair` mints, `glissa pair --list` shows devices, `glissa pair --revoke <id>` revokes; the CLI lives in `server/pair-cli.js` (not `bin/`, whose files are whitelisted one by one in package.json). Two processes write this file (the CLI mints and revokes, the server redeems), so every write takes an `O_EXCL` lockfile beside it, re-reads inside the lock, and commits with an atomic tmp+rename; a write that cannot take the lock fails rather than racing, and a lock older than 5s is treated as abandoned. Request-path reads never touch the disk: they hit an in-memory snapshot refreshed both by a debounced `fs.watch` (usually sub-second) and by a 30s reload interval, so a revocation applies with no restart even if the watcher never installed. That interval is the guarantee `glissa pair --revoke` quotes. A corrupt file fails CLOSED (no devices = 401) and blocks writes rather than overwriting it. `lastSeenAt` lives in a separate server-owned `pairings-seen.json`, throttled, display-only, never consulted for auth.
- **Server-machine side effects refuse remote callers.** The upgrade handler stamps the connection's trust onto the control `ws` (`ws.glissaTrust`), which is how a handler tells a paired phone from the local dashboard and refuses an action whose only effect would land on the server machine; it comes from the socket's local port like every other trust read, never from anything the client sent. Absent trust (remote mode off) reads as local, so local behavior is unchanged.
- **Remote config is unreachable from the control WebSocket.** `remote` is in no settable key list, is not echoed by `getSettings`, and is not read by `applySettings`, so an unauthenticated local socket cannot turn remote access on or repoint it (`tests/control-settings-remote.test.js`). Config file or CLI only, restart required.
- **Origin policy.** `server/core/origin-policy.js decideOriginAllowed` replaced the inline `isAllowedOrigin`; with an empty `allowedOrigins` it reproduces the old decisions exactly (pinned against a copy of the original function in `tests/origin-policy.test.js`), and adds exact-match plus leading `*.` host-wildcard entries. A DISABLED remote block contributes no origins at all, even one with a leftover `publicHost`, so switching remote off restores the pre-remote origin behavior exactly.
- **Binding wider is refused.** A non-loopback `GLISSA_HOST` aborts boot unless `GLISSA_INSECURE_BIND=1` states the intent (`decideBindHost`, `tests/remote-config.test.js`).
- **Dev mode is not supported.** The Vite plugin never calls `attach()`, so remote mode is inert under `npm run dev` by design.
- **Integration suite.** `npm run test:container` builds `test/container/Dockerfile` and runs `test/container/remote-mode.sh` on Linux: local 200 / remote 401, mint, redeem with an HttpOnly cookie, cookie access, replay 403, WS with and without a cookie, Origin allow and refuse, `--list`/`--revoke` propagating without a restart, an expired token refused, and a remote-disabled restart. Plain `npm test` stays Docker-free.

### Session Identity

Sessions are keyed by a stable UUID (`id`), not the mutable display `name`. The `id` is auto-assigned on first load (via `ensureProjectIds`) and persisted to `config.json`. All Maps, WebSocket routes, and control messages use `id` as the primary key. The `name` is display-only and can be changed via inline rename.

### Dual WebSocket Architecture

- **Data WebSocket** (`/terminals/:sessionId`): Raw PTY bytes bidirectional. One per session per client.
- **Control WebSocket** (`/control`): JSON messages for state-change, snapshot, kill, restart, rename.
- **The split is deliberate; do not merge the channels.** The two want opposite loss policies (data bytes drop recoverably from the ring and backfill by offset; control JSON must not drop and replays one-shot types), `bufferedAmount` is per-socket so one shared buffer cannot tell which class stalled, and one merged TCP stream would let a PTY output flood head-of-line-block a kill or notify frame. Merging would also force a demux framing protocol onto what is today a raw byte pipe. Reviewed and kept 2026-08 (see `docs/architecture-review.html`, section 1).
- xterm.js in the browser connects to data WebSocket; control panel uses control WebSocket.
- **Resize is arbitrated by ACTIVE VIEWER, not last write.** A session owns one PTY but any number of data connections (a second tab, a paired phone), so a `{type:'resize'}` from whoever just became visible reflows the terminal everyone else is looking at. Last-write-wins is right while every viewer is watching, and wrong the moment one stops: the client caches its last sent cols/rows and its own box never changed, so a desktop left at ~40 cols by a phone opening the same session stayed there forever. The server therefore records each connection's declared size, and the viewer that stops looking sends `{type:'unview'}` (the connection stays open, bytes keep flowing into the card) or simply closes; either way the most recent SURVIVING viewer's size is re-applied, and no survivor leaves the PTY as it is. The pick is pure (`server/core/viewer-size-core.js`, ordered by a monotonic sequence because two clients resizing in the same millisecond is ordinary), the wiring in `backend.js` is thin. Clients send `unview` from the seams that already know a card stopped being visible: `card-host.releaseCard` and the phone shell leaving the Terminal screen. `ui._unviewTerminal` (in `session-card/terminal.js`) is a no-op for a card that never claimed a size (a board-only phone), and drops the resize cache with the claim so the card re-asserts when it becomes the visible viewer again at the same dimensions.

### Dashboard Rendering (xterm.js)

- Each session card contains an xterm.js Terminal instance
- xterm.js handles ALL ANSI rendering - server is a dumb pipe
- `@xterm/addon-fit` for resize, `@xterm/addon-webgl` for GPU rendering
- Vite bundles @xterm/* for production; dev mode proxies to Express
- Status detection does NOT tap the rendered body; it scans only OSC-0 titles (fallback) and consumes Claude Code hooks (authoritative). See "Status Detection" above.

### Two First-Class Layouts (desktop / phone)

The dashboard has two layouts, not one responsive shell. `public/form-factor-core.mjs` `decideLayout({ coarse, narrowWidth })` is the ONE predicate: `'phone'` requires a coarse pointer AND a viewport at or below 768px. The AND is the point - a desktop window dragged to 500px keeps the three-panel IA (the operator can widen it back), and a coarse-pointer TABLET above 768px also stays desktop (it has room for the docked rail + terminal + sidebar, and the touch corrections in `style.css` are keyed on the pointer alone). `public/form-factor.js` evaluates the two media queries, stamps `<html data-layout>` at boot and on every live change (orientation), and notifies subscribers.

- **All phone styling keys off `[data-layout="phone"]`.** There is no `max-width` override of a desktop selector; a bare `max-width` block is reserved for content that must wrap in a narrow DESKTOP window (settings tabs, long strings).
- **The desktop shell is `display:none` on a phone.** `public/phone/phone-shell.js` renders seven screens (Board, Terminal, Review, Radar, PRs, Usage, Visions) behind a bottom nav (Radar, PRs, Usage and Visions are nested under a More item, so the nav row stays five targets). Board is the base screen; entering another pushes exactly ONE history entry, so the back gesture always means "return to the Board". History is untouched on desktop.
- **Nothing is duplicated; live elements are RE-PARENTED.** The review sidebar (`reparentReviewPanel`), the Radar, PRs, Usage and Visions panels, the desktop header's controls (connection chip, "+ Session", help, the hamburger with its client-trust gating) and the focused session's card all MOVE into the phone screens and move back on the flip out (`dom-helpers.js` `adoptElement` / `releaseElement`). A second copy would mean a second state pipeline for the same facts. The phone Board reads the same `session-card/card-registry` the desktop cards read and is refreshed by the same `app.js` control-WS handlers.
- **One card-borrow seam, one borrower.** `public/card-host.js` `borrowCard` / `releaseCard` is shared by the Focus center and the phone Terminal screen; a session owns one xterm, so the single-borrower invariant is GLOBAL and a layout flip hands the card across cleanly instead of stranding a live terminal in a hidden subtree.
- **Board order is attention-first** (`public/phone/triage-core.mjs`), the deliberate opposite of the desktop rail's stable identity order: a rail is stared at for hours and needs a fixed spatial map, a phone is picked up for a minute to answer "who needs me". The ORDER is phone-specific; the "needs you" RULE behind the `{n} NEED YOU` readout is not, and lives once in `public/focus-view/attention-core.mjs` (WAITING plus an unopened COMPLETE) so the rail head and the Board can never report two numbers under one sentence.
- **Soft keyboard.** The phone shell is sized from `window.visualViewport`, not `100dvh`, so an open keyboard RESIZES the terminal (and the card's existing ResizeObserver refits cols/rows) instead of covering its last rows and the nav.
- **Touch scroll is ours, because xterm has none.** xterm 6.0.0's viewport is a VS Code `SmoothScrollableElement` driven by wheel and mouse; there is not one touch listener in that path, so a finger drag over a terminal moves nothing on any device. `session-card/touch-scroll.js` claims a vertical drag under `[data-layout="phone"]` only, after a threshold that leaves a tap and a long-press selection to the browser (the gesture math is pure, in `touch-scroll-core.mjs`: threshold, vertical dominance, row quantization with a carried sub-row remainder, and the release-flick physics). The normal buffer scrolls via `term.scrollLines`, uncapped, and a released flick COASTS: the shell samples the last few move positions, `releaseVelocity` turns them into signed px/ms, and a `requestAnimationFrame` loop decays it by the VS Code `Gesture.SCROLL_FRICTION` (0.005 px/ms per ms, the same machinery xterm master's own touch path adopts) through the same quantization core. The coast is cancelled by a new touch, a teardown (`termWrap` off the document), a layout flip off phone, the viewport hitting the end of the scrollback, or the drag routing to the application. Inertia is scrollback-ONLY, and the per-move row cap survives only on the wheel path: every coasted row there would cost the application a mouse report or arrow key plus a full-screen redraw. Row height is measured from `.xterm-screen`, not `.xterm`, whose padding in some card layouts would overstate it and make the buffer trail the finger. The alternate buffer has no scrollback, so the drag is re-emitted as one synthetic `DOM_DELTA_LINE` wheel notch per row on `term.element` and xterm's OWN wheel listeners decide the meaning: an application tracking the mouse gets a wheel button report, one that is not gets the `ESC[A`/`ESC[B` fallback (`CoreBrowserTerminal.bindMouse`). Hand-rolling that choice here would drift from xterm's the first time it changes. `touch-action: none` on the phone terminal box is load-bearing: under the slot's inherited `manipulation` the browser can claim the pan first and hand the listener a non-cancelable move.
- **Predictive text bypasses xterm's input path.** xterm 6.0.0 mishandles the events a phone keyboard sends for autocorrect, suggestion picks and word deletion: `CompositionHelper._handleAnyTextareaChanges` diffs its helper textarea with an unanchored `String.replace` (a corrected word is APPENDED to the one it replaced) and collapses every shrink to a single DEL regardless of how many characters went away, while `CoreBrowserTerminal._inputEvent` forwards only `inputType: 'insertText'` and drops `insertReplacementText` outright. Upstream `xtermjs/xterm.js#3600` is open and unowned. `wireSoftKeyboardInput` in `session-card/terminal.js` `wireSoftKeyboardInput` therefore takes the TEXT path off xterm under `[data-layout="phone"]`: capture-phase listeners on `termWrap` (an ancestor of the helper textarea) run before xterm's own listeners on the textarea itself, so `stopPropagation` keeps the fragile path from ever seeing the keydown / composition / input event, and the bytes come from a shared-prefix diff of the textarea instead (`session-card/ime-core.mjs`, pure, code-point granular so one astral character costs one DEL). The textarea is READ, never cancelled: a `beforeinput` raised by autocorrect or an IME is allowed to be non-cancelable, so the byte stream is reconciled after the fact from the value. Only the TEXT path moves: a real keydown (Enter, Backspace, arrows, Ctrl combos) still reaches xterm untouched, with any pending composed text flushed ahead of it. The diff baseline is dropped by `ui._resetSoftKeyboardBuffer`, which `sendTerminalInput` calls for every write that did NOT come from the soft keyboard (the touch key strip, a paste, xterm's own key handling), because those edit the input line without editing the textarea; a backward-deletion `inputType` arriving against an already-empty textarea then falls back to one DEL (or ESC+DEL for a word delete) since there is nothing left to diff. Accumulation stays bounded to one input line because xterm blanks the textarea itself on Enter and Ctrl+C. Nothing is intercepted on desktop, where the layout check fails and every handler only resyncs its baseline: the same takeover there would regress CJK composition, which is exactly what kept the equivalent upstream fix (`xtermjs/xterm.js#4173`) out.

### WebSocket Transport

Use the `ws` package directly. Do NOT use Socket.IO or any abstraction over WebSockets.

## Coding Style

- CommonJS only: `const x = require('x')`, `module.exports = { ... }`
- No classes unless the pattern genuinely requires instance state
- Prefer explicit over clever
- Error handling: propagate errors via EventEmitter `error` events or callbacks, not thrown exceptions in async paths
- Keep functions small and single-purpose

## Parallel Agent Work (worktree isolation)

When fanning out multiple agents to edit this repo concurrently (Claude Code native teams or several spawned agents), give each agent its own git worktree (Agent `isolation: "worktree"`) and integrate the lane back once it is clean. This avoids working-tree collisions between concurrent lanes.

- This is a working convention for editing Glissa. It does not use the OMC `omc team` / tmux runtime (tmux is unavailable on native Windows).
